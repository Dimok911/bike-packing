### 1. Общий путь личного сохранения — в работе, выключенный пилот

Продолжение 2026-09-07 — отдельная подготовка первоначального старого списка:

- Backend `7e13f7b` / paired-проверка `00c5b1a`: `list.migrate` — десятый вид
  личного действия. Чтение не делает backfill. SELECT-only preview фиксирует
  revision, исходный legacy hash и полный итоговый снимок с его hash. Запись

Промежуточная реализация 2026-09-06:

- `personal-save-outbox.js`: снимок + действие одной синхронной записью до
  локального зеркала; отдельные неизменяемые ключи, зависимости без часов,
  сохранение обеих ветвей при гонке вкладок и остановка на конфликте/повреждении.
- В `app.js` подключены gated persistence/load/save/manual-sync hooks для уже
  известного личного списка. Незавершённый журнал восстанавливается раньше
  обычного локального зеркала; старые прямые записи и загрузки фото блокируются.
- Отправка предшественников получает только историческое подтверждение,
  не применяет их данные к интерфейсу. Последнее действие проходит проверку
  текущей серверной версии, аккаунта/локального поколения и локальный checkpoint.
- Явный UUID теперь распознаётся после смены поколения редактора; тот же UUID
  с другими данными блокируется. Неизвестный результат не разрешает новый POST.
- `PERSONAL_SAVE_OUTBOX_ENABLED = false`; остальные release gates также false.
  Это НЕ завершение пункта: первичное создание через реальный UI, восстановление/
  конфликты с новой серверной базой, файлы, полная пользовательская проверка и
  политика хранения больших журналов ещё требуют адаптеров и тестов. Список
  с фото в пилоте останавливается, а не отправляет незавершённый составной пакет.
- Модуль/обёртки проверены unit-тестами, браузерный стенд очереди — Chromium и
  mobile WebKit (14 сценариев). Стенд не заменяет полный проход реальных кнопок.

### 8. Восстановление из истории

Продолжение 2026-09-07 — явный отказ от отклонённого восстановления:

- После проверки точных terminal receipts ручная синхронизация предлагает
  оставить актуальную серверную версию. Автосохранение не открывает окно и не
  принимает решение. Отмена сохраняет восстановление и последующие локальные
  изменения; согласие явно отменяет их и создаёт НОВОЕ действие с прочитанной
  revision. Старый restore не перебазируется и не отправляется под новым ID.
- Ещё неизвестный потомок сначала получает точное подтверждение без эффектов
  из-за отклонённого предшественника. Пока результат неизвестен, выбор не даёт
  права очистить очередь. Второе изменение сервера требует нового сравнения
  и нового согласия; lost ACK восстанавливается прежним UUID. Старые действия
  хранятся до подтверждения преемника. После отказа можно заново выбрать историю.
- Локальный сертификат решения допускает только точную серверную бизнес-копию;
  он не разрешает последующую потерю чужих/невыбранных записей. Фото, смена
  аккаунта/редактора, неверная структура и quota останавливают решение. При quota
  в диагностической копии сохраняется полный выбранный кандидат.
- Проверено: 215 transport, 889 critical, source check; новые реальные UI окна —
  4/4 Chromium + mobile WebKit. API/MySQL 44/44: restore → ещё не отправленный
  потомок, no-effect receipt, отмена, новое серверное изменение во время выбора,
  новое решение → lost ACK → reload/GET без нового POST. Прежние UUID/байты
  сохранены, поздний старый restore не применён. В первом варианте paired-теста
  был пропущен обязательный callback `onCaptured`; исправлен тестовый стенд,
  а не ослаблены проверки очереди.

  134 браузерных сценариев запускается отдельно; здесь не заявлен его результат.

### 12. Итоговый аудит обходных путей и состояния очереди

Продолжение 2026-09-07 — длинная цепочка при обратной доставке:

- Воспроизведена локальная остановка A → B → C → D: после доставки D, C
  очередь не выпускала B, потому что учитывала только прямую связь. Теперь
  вычисляются направленные предки/потомки по сохранённым намерениям того же
  аккаунта и списка. Ожидающий потомок не блокирует нужного ему предшественника.
- Общий предок не делает две ветки последовательностью. Нет разрешения обходить
  неизвестную квитанцию самой операции, выдумывать отсутствующую связь или
  использовать промежуточную запись другого списка. UUID и полные данные
  проверяются до сверки остальных действий. Серверные revision/dependencies
  по-прежнему окончательно решают порядок внутри транзакции.
- 290 transport, source check; новый браузерный сценарий 2/2 Chromium/mobile
  WebKit: обратная доставка четырёх действий, reload, смена RU/EU, lost ACK,
  отсутствие нового POST для неизвестного результата, точные waiting-повторы.
  Реальный API/MySQL 83/83: дерево теперь доставляется в обратном порядке через
  настоящий frontend queue, не прямой тестовый запрос. В первой версии теста
  исправлен лишний API-префикс виртуального пути; рабочие проверки не ослаблены.
- Локальный срез дерева frontend `9d9bdfd` / backend `0ffff76` предшествует этому
  усилению очереди. Общий финальный прогон выполняется отдельно. Этап 12 целиком
  не закрыт; публикаций, push, live-миграций и включения release gates не было.

## Когда отмечаем пункт выполненным

Одновременно выполнены: подключены реальные действия интерфейса, сохранены
данные и зависимости до отправки, есть соответствующий серверный обработчик,
пройдены проверки перезагрузки/повтора/потери ответа/перестановки запросов и
смены аккаунта. Для составных действий дополнительно проверены частичный пакет
и точная версия источника. Фиксируем изменённые файлы, пару frontend/backend
коммитов и результаты тестов. «Проверен отдельный модуль» не закрывает пункт UI.

Изменения темы, открытие модалок и другие действия без записи бизнес-данных
не превращаем автоматически в серверные операции. Каталог, Shared Auth, proxy
и deployment остаются вне этого списка реализации до отдельного разрешения.
