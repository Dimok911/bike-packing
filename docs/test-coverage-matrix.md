# Карта автоматических проверок Bike Packing

Эта карта перечисляет пользовательские функции по отдельным сценариям. Она нужна,
чтобы слово «проверено» всегда означало конкретный уровень проверки, а новые
функции не оставались только на ручной проверке.

## Что означают уровни тестов

### Контрактные тесты — 801 проверка

Контрактный тест берёт отдельное правило или механизм программы и проверяет его
на заранее подготовленных данных. Например: нельзя удалить заблокированную
укладку, конфликт версий должен быть обнаружен, итоговый вес должен считаться
одинаково до и после сохранения, а офлайн-сессия не должна открыть данные другого
пользователя.

Они запускаются без кликов по настоящему браузеру и без production-БД, поэтому
работают быстро и точно показывают, какое правило сломалось. Число **801** — это
количество выполненных тестовых проверок, а не 801 протестированная функция и не
процент покрытия. Один пользовательский сценарий может состоять из десятков
контрактов, а наличие контракта не доказывает, что соответствующая кнопка
правильно подключена в интерфейсе.

### Браузерные E2E — 5 сценариев

E2E-тест открывает приложение в настоящем изолированном Chromium и действует как
пользователь: нажимает кнопки, заполняет формы, перезагружает страницу и читает
результат на экране. Сейчас браузер проверяет:

1. создание укладки, сумки и вещи с сохранением после перезагрузки;
2. редактирование названия сумки, названия и веса вещи;
3. поиск вещи и очистку поиска;
4. режим сбора и сохранение отметки «собрано» после перезагрузки;
5. безвозвратное удаление вещи.

Эти пять сценариев изолируют запросы к API и используют гостевое локальное
хранилище. Поэтому они хорошо проверяют браузерный интерфейс и localStorage, но
пока не доказывают совместную работу интерфейса, авторизации, API и MySQL.

### DB/API smoke — 1 сквозной серверный сценарий

DB/API smoke создаёт одноразовую MySQL 8.4, применяет реальную схему, запускает
настоящий API и обращается к нему по HTTP. Он проверяет:

- health/capabilities и запрет анонимного доступа;
- сессию из БД;
- создание и чтение полной укладки из таблиц сущностей;
- изоляцию данных двух пользователей;
- увеличение ревизии и ответ `409` устаревшему клиенту;
- историю и восстановление;
- сохранность данных после перезапуска API;
- каскадное удаление укладки, сущностей и истории.

Тест не использует production-БД: имя базы обязано оканчиваться на `_test`,
production-хосты запрещены, а база удаляется после прогона. Smoke доказывает, что
основной серверный путь жив, но не заменяет детальные тесты всех endpoint и не
нажимает кнопки frontend.

## Обозначения матрицы

- **Да** — сценарий автоматизирован на этом уровне.
- **Частично** — проверена только часть цепочки.
- **Нет** — автоматической проверки пока нет.
- **Устройство** — требуется дополнительный ручной прогон на iPhone/Safari.

## Приоритет следующих пакетов

1. **P0 — ежедневный локальный CRUD:** удаление укладки и сумки, вложенная
   сумка, перенос/копирование вещи, точные расчёты веса, фильтры и «всё разобрать».
2. **P0 — frontend + настоящий API:** вход тестовой сессией, сохранение в MySQL,
   reload из API, конфликт двух браузеров и изоляция пользователей.
3. **P1 — фото и шаблоны:** реальное временное photo storage, upload/read/delete,
   копирование demo/shared и admin publish/unpublish.
4. **P1 — история и backup:** восстановление через UI, download/upload архива.
5. **P2 — PWA и устройства:** offline service worker в Chromium, затем ручной
   Safari/iPhone smoke для touch, viewport и установочного режима.

## Когда запускаются проверки

- `npm run check` и `npm run test:critical` — перед frontend-сборкой.
- `npm run test:e2e` — все браузерные Chromium-сценарии.
- GitHub Pages deployment запускает source-check, 801 контрактную проверку,
  все E2E и сборку; публикация начинается только после их успеха.
- Pull request запускает тот же набор без публикации.
- Репозиторий `bikepacking-api` отдельно поднимает MySQL 8.4 и запускает DB/API
  smoke на push в `main`, pull request и вручную.

## Правило для новых функций

Каждое новое пользовательское действие добавляется в эту таблицу отдельной
строкой. Для предметного правила нужен контрактный тест, для критической цепочки
через интерфейс — E2E, а для изменения API или хранения — DB/API-тест. Если
сценарий зависит от touch/Safari, автоматический тест дополняется проверкой на
реальном устройстве.
