# Короткая проверка двух вариантов WebKit в Linux

11.09.2026. Дополнение к `browser-ci-diagnostics-2026-09-10.md`.

В ручном запуске `Frontend quality` появился параметр `webkit_diagnostic`.
Он выбирает два отдельных Linux runner: headless WPE и GTK под Xvfb. Выбор
движка подтверждён [launcher Playwright v1.62.1](https://raw.githubusercontent.com/microsoft/playwright/v1.62.1/browser_patches/webkit/pw_run.sh):
аргумент `--headless` выбирает WPE, запуск без него — GTK.

Оба runner выполняют одни и те же четыре существующих сценария составной
фотоформы: создание, перемещение, количество и удаление размещения, по пять
повторов. Используется обычный мобильный проект и исходные проверки результата,
один worker, ноль повторных попыток после ошибки, остановка после трёх отказов.
Собирается только нужный вариант приложения `photo-edit`. Ограничение job —
45 минут с установкой зависимостей.

В артефакты входят отчёт, первые отказы/трассы, сведения о жизни страницы и
метрики Linux/ядра. Обычный запуск quality сохраняет прежний полный набор;
диагностический параметр по умолчанию выключен. Текст прежних шагов сверен
побайтно после удаления добавленного условия, shell проверен `bash -n`.

Этот опыт проверяет связь сбоя с вариантом WebKit и средой. Успех короткого
набора сам по себе не устраняет нативный дефект и не закрывает приёмку.
Публикация, release-флаги и обработчики приложения этим параметром не меняются.

Первый запуск: [34607110272](https://github.com/Dimok911/bike-packing/actions/runs/34607110272),
FE `9d855e60`. WPE **20/20**, GTK **3 failed / 17 not run**. Во всех трёх
GTK-трассах нет page crash/page error; ядро не зарегистрировало segfault,
OOM-счётчики нулевые. Отказы — пятисекундное ожидание `dirty=false`, пока
синхронизация ещё идёт. В create окончательное чтение состояния завершилось
через 5,99 с после клика, в quantity — через 5,48 с; при move финальное чтение
к остановке теста ещё не началось. Это не прежнее падение ThreadedCompositor.

Ожидание завершения именно этих составных форм увеличено до 30 секунд.
Проверки числа действий/файлов, полей, размещения, reload и ошибок страницы
сохранены; повторов после отказа по-прежнему нет. Результат повторной диагностики
будет записан отдельно. Короткий успех WPE не закрывает нативную проблему.
Локальный контроль ожидания: **8/8** Chromium/mobile WebKit без повторов и
пропусков, `resume-webkit-form-wait-ui-1.txt`, 3,1 минуты. Linux GTK проверяется
отдельным запуском CI; локальный прогон его не заменяет.

Повторный запуск [34609363777](https://github.com/Dimok911/bike-packing/actions/runs/34609363777),
FE `78d2802b`: WPE **19 passed / 1 failed**. Отказ `move`, повторение 1,
произошёл в подготовке исходной вещи при клике `#createItemForContainerBtn`,
ещё до фотоформы. Трасса сообщает `Target crashed`; ядро — один segfault
`ThreadedCompositor` по прежнему смещению `0x5fd556a` в
`libWPEWebKit-2.0.so.1.10.2`, OOM 0. Артефакт `10267223401` и журнал
`webkit-wpe-diagnostic-2.txt` сохранены. GTK **20/20**, 11,1 минуты, без
повторов/пропусков: `webkit-gtk-diagnostic-2.txt`. Общий результат запуска —
failure из-за WPE; короткий набор GTK не заменяет полную приёмку.

Сверен открытый [upstream #42637](https://github.com/microsoft/playwright/issues/42637)
от 09.09.2026: независимый пример с вложенными окнами, нулевым чтением
на потоке композитора и похожим отказом клика. В отчёте воспроизводится и
Playwright 1.63.0; несколько переключателей рендеринга сбой не устранили.
Сходство наблюдений не доказывает тождество функций в разных сборках без
символов. Обновление версии или переключение движка не объявляется исправлением.
