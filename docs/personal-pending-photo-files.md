# Новые файлы в следующей ожидающей фотоформе

Срез принят локально: API 2d36554, frontend — коммит с этим документом.
Предыдущая FE основа a21d4d4. Публикация и включение флагов не выполняются.

У вещи/сумки можно зафиксировать следующую форму с новыми файлами, пока
исходная форма ещё отправляется. Следующая форма хранит полный снимок того же
владельца и ссылку на непосредственное предыдущее действие. Между фотоформами
и после них допускаются уже подключённые изменения полей. У каждой формы
свои неизменяемые UUID и отдельная запись со всеми новыми файлами.

`ownerResult.version=1` хранит непосредственный operationId и полного владельца.
Неизвестные версии владельца/удаляемого фото остаются null в исходном запросе.
Сервер проверяет точный результат предшественника и заблокированные строки,
после чего подставляет реальные числовые версии только в приватную копию
исполнения. Исходное действие, digest и повторный запрос остаются неизменными.
DB-потомки такой фотоформы используют `photoResults.version=6`; обычная v5
сохраняется для предыдущего пути.

Собственный FE `PERSONAL_PHOTO_FORM_OWNER_RESULT_ENABLED` по умолчанию false.
Серверное включение — `BIKE_PACKING_CAUSAL_PHOTO_FORM_OWNER_RESULT_ENABLED=1`
при включённой исходной цепочке photo-form. Capability:
`personalCausalPhotoFormOwnerResultV1`. Исторические записи доступны для чтения
при выключенных новых writer gates.

Временный synced статус используется только внутри проверки грамматики.
Настоящий serializer получает исходные pending-ссылки, поэтому им не
приписываются вымышленные URL, размеры или серверное подтверждение. Полный
candidate и проекция повторно проверяются после восстановления исходных ссылок.

Отмена сначала проверяет все локальные файлы и читает точные stage-квитанции.
Фотоформы обрабатываются от предка к потомкам: неоднозначная загрузка может
быть закрыта только своим владельцем. Если хотя бы одна фотоформа отклонена,
затем отдельно отменяются DB-шаги с их исходными UUID. Уже подтверждённые
формы сохраняют свой результат. Выбор серверной версии — отдельное явное
решение. Потерянный ответ не удаляет файлы и не создаёт новые действия.

Пройдены UI-7 28/28 Chromium/mobile WebKit, 8,4 минуты: подтверждение, lost file,
lost first/second owner, quota, отмена и потерянный ACK отмены. В каждой цепочке
есть отдельный DB-потомок v6. UI-6 отдельно проверил четыре отмены в Chromium.
API/MySQL-4 242/242, 351,10 с, MySQL остановлен; 92 operations, 74 source/service.
632 transport (pending-files-transport-5.log), 896 critical
(pending-files-critical-1.log) и FE check-4 завершились успешно.
Регрессия-1 при выключенной новой возможности: 18/18 Chromium/mobile WebKit,
обычные формы create/edit, fileless delete-order и выключенный источник каталога.
API-1/2/3 выявили пропуски тестовой связки (наблюдаемая базовая версия и
обязательный onAdopted), исправленные без ослабления рабочих проверок.
UI-1/2 выявили ошибочную переменную runtime и несовместимость временного
synced с serializer; UI-4/5 уточнили порядок отмены и тип ошибки неизвестного stage.

Третья фотоформа через DB-шаг и fileless manufacturer источник проверены
отдельными тестами настоящего compiler/session/codec/outbox. Общий аудит,
fileless правка самих ожидающих фотографий и public/shared/admin источники
относятся к следующим этапам; этот срез не закрывает весь переход.
