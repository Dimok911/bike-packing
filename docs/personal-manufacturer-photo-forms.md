# Сумка производителя как сохранённая форма

Локальное продолжение после FE 29e1319 / API 1311c1a. Отдельный выключенный
флаг `PERSONAL_MANUFACTURER_PHOTO_FORM_ENABLED` и серверная capability
`personalCausalManufacturerPhotoFormV1`. Содержимое каталога не меняется.
Deployment, push и включение возможностей на рабочих серверах не выполняются.

До первого чтения картинки фиксируется полный выбранный каталоговый entry
со всеми полями, включая неизвестные адаптеру, и ограниченный пользовательским
лимитом упорядоченный набор URL. Ошибка любого выбранного файла останавливает
весь выбор. Изменение формы, аккаунта или нового выбора не позволяет позднему
результату заменить текущий ввод. В этом пути файлы попадают в существующий
контроллер фотоформы, который сохраняет их вместе с действием до закрытия окна.

SAVE содержит `manufacturerSource: {version: 1, entry, imageUrls}`, обычные
поля карточки, итоговый набор файлов и при необходимости полный контекст
размещения сумки. После выбора пользователь может менять обычные поля; данные
об источнике остаются рассчитанными по первоначальному каталогу. Повтор не
читает свежий каталог или картинки. Сервер добавляет manufacturerCatalogSource
к новой личной сумке в той же транзакции, что и фото, укладку, историю и квитанцию.

Чистый проектор источника скопирован одинаковым файлом в API. Его вычисление
происхождения сравнивается с действующим производственным преобразованием
на всём существующем каталоге с фотографиями. Сервер не загружает исходные URL
и не изменяет каталог производителя; данные источника относятся к частной копии.

Клиентские guard и capability проверяются до отметки отправки. Точное чтение
уже сохранённого результата работает с выключенным флагом; отсутствие
manufacturerCatalogSource или изменение его значений не принимается за успех.
Проверки настоящей БД инъецируют ошибку последней записи квитанции и проверяют
откат владельца, происхождения, фото и размещения; потерянные ACK и restart
проходят через настоящий frontend codec/outbox/queue.

Удаление всех выбранных фото перед SAVE сохраняет ту же полную запись источника
с пустым набором файлов. Новая сумка имеет исходную entityRevision 0; выдуманной
версии существующего владельца нет. Такая форма проходит обычный outbox без
staging. Результат содержит доказательство происхождения, необходимое для
зависимых DB-правок. Отмена fileless формы сохраняется до отдельного выбора
серверной версии, включая потерянный ответ, reload и restart API.

Входные данные проходят строгую JSON-проверку до клонирования и чтения картинки:
NaN, Infinity, undefined, Date, BigInt, функции, разреженные массивы и циклы
не могут незаметно изменить сохранённый источник. Общая проверка JSON вынесена
из существующей проверки payload; ограничения размера отправки не менялись.

Проверено локально:

- 614 transport (manufacturer-transport-4.log), 896 critical
  (manufacturer-critical-4.log), FE check (manufacturer-check-5.log).
- API 83 operations, 74 source/service; API/MySQL **235/235**, 345,80 с
  (manufacturer-mysql-2.log), exit0, одноразовая MySQL остановлена.
- UI **20/20**, 3,4 мин (manufacturer-ui-4.log), Chromium/mobile WebKit:
  успех, lost file/owner ACK, quota, ошибка второго файла, изменение формы,
  fileless SAVE/lost ACK/quota и отмена с отложенным выбором после reload.
- Регрессия **18/18**, 4,1 мин (manufacturer-ui-regression-4.log): выключенный
  новый source gate, обычные create/edit формы и fileless delete/order. Оба
  браузерных процесса exit0, завершены. API-коммит d9a48e0; frontend — коммит,
  содержащий этот документ. Последующая чистая JSON-проверка источника в plan
  дополнительно проверена модульным прогоном, включая валидный полный codec.

Первый API-прогон с файлами прошёл 233/233; затем добавлены fileless сценарии.
UI-2 остановился на неверном ожидаемом числе запросов: счётчик учитывает также
отдельный cancel POST. Проверка теперь отдельно сверяет его UUID; UI-3 прошёл.
Регрессия-1 ожидала окно восстановления до сохранения действия, хотя preflight
показывает предупреждение и оставляет исходную форму открытой. Проверка уточнена
на сохранённые поля/фото, предупреждение и отсутствие запросов; guard не ослаблен.
Регрессия-2/debug воспроизвела false вместо null в helper источника при выключенных
дополнительных режимах. Это ломало чтение action.kind до отправки обычной формы;
helper исправлен. Регрессия-3 прошла 9 Chromium сценариев, затем выявила переход
в старый каталожный путь в Windows WebKit. Source gate теперь останавливает выбор
до чтения фото и старого Blob cache, оставляет исходную форму и показывает
предупреждение. Регрессия-4 полностью прошла. Старый Blob cache не переделывался.

Это только личная новая сумка из каталога производителя, с размещением и
последующими DB-правками. Новые файлы в следующей неподтверждённой форме,
публичные шаблоны, sharing и административные операции остаются отдельной
работой. Разделы 02/06/07 и весь checklist не объявляются завершёнными.
