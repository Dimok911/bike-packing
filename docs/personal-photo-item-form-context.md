# Составная личная форма вещи с фотографиями

Локальная разработка от 2026-09-09. Публикация и включение флагов не входят
в этот этап. Общий список перехода остаётся в работе.

Форма новой или существующей личной вещи может фиксировать поля, новые
фотографии либо удаление/порядок прежних фото, доступность, размещение и
количество в выбранной укладке одним действием `photos.mutate/action=form`.
Неизменённые фотографии с правками только полей остаются на принятом DB-пути.

## Граница действия

Необязательный `body.formContext` версии 1 содержит `availabilityStatus` и
`placement`. Последний равен null для изменения только доступности либо
содержит полный выбранный `targetLayout`, `targetContainerId`, положительное
целое `quantity` и явные поля времени/устройства `layoutFields`.

Полный выбранный снимок, базовые числовые версии, номера действия и файлов
фиксируются до асинхронного чтения владельца или хранилища. UUID обозначают
тождество, а не порядок. Чтение подтверждает исходную версию; более новая
укладка не подставляется в старую операцию.

Общий компилятор проверяет целостность дерева, полный порядок, количества,
отсутствие чужих/public владельцев и блокировку укладки. Изменять закрытую
укладку или переносить недоступную вещь в другую сумку нельзя. Он сохраняет
неизвестные поля выбранной укладки и остальных владельцев. Изменение одного
количества сохраняет порядок и отметку упаковки; перенос или снятие удаляет
прежние ссылки и отметку. Семантика сверена с существующими операциями укладки.

После расчёта локальные зеркала активной укладки обновляются только из
проверенного результата. Обычная сериализация должна воспроизводить ровно
этот результат. Нормализация и скрытое исправление исходного дерева запрещены.

## Сохранение и восстановление

Прежний бинарный журнал хранит все исходные файлы вместе с расширенным
неизменяемым manifest. До подтверждения всех файлов сервер не получает
операцию владельца. Сервер повторяет проверку полного выбранного снимка в
той же транзакции, где сохраняются поля, размещение, фотографии, история и
receipt. Подтверждение проверяет также доступность и полный результат укладки.

Неизвестный результат, перезапуск, нехватка места для журнала и повторное
нажатие сохраняют исходную операцию и байты. Точное чтение прежнего receipt
остаётся доступным при выключенном сохранении новых составных форм.

Отдельный false gate: `PERSONAL_PHOTO_ITEM_FORM_CONTEXT_ENABLED`.
API: `BIKE_PACKING_CAUSAL_PHOTO_ITEM_FORM_CONTEXT_ENABLED=1` вместе со всеми
родительскими фотофлагами; capability `personalCausalPhotoItemFormContextV1`.
Без capability очередь не регистрирует запись владельца. Уже подготовленные
файлы при этом остаются в журнале; отсутствие capability само по себе не
является отменой их staging.

## Проверки и оставшаяся работа

10 targeted проверок расчёта/формы/кодека/восстановления, 54 queue, 896 critical,
75 API operations, 74 API source/service и FE source check прошли.
Полный API/MySQL прогон: 212/212, 229,61 с (item-photo-context-mysql-2.log).
Первый прогон остановил новый fixture неверным ожиданием HTTP 404 вместо
200/operation.state=unknown; зависимые тесты не включили свой gate. Исправлено
ожидание fixture, после чего все новые и прежние проверки прошли.
Заключительный Chromium/mobile WebKit прогон: 26/26, 5,3 мин
(item-photo-context-ui-4.log): создание/перенос/количество/снятие, потеря
подтверждения файла и владельца, quota, удаления фото без новых файлов и
восемь обычных форм. Все процессы завершены. UI1 исправлен blur перед
мобильным tap; UI3 не собрал нужный photo-form bundle, UI4 собрал оба режима.
Изменения приложения для обхода этих тестовых ошибок не потребовались.

Этот срез не закрывает составные фотоформы сумок, добавление новых файлов
к ещё неподтверждённому переносу, публичные источники и остальные главы
`ui-causal-operations-checklist.md`. Флаги в исходниках остаются false.
