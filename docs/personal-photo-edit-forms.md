## Граница среза

Личная существующая вещь/сумка: поля и удаление сохранённых фото либо новый
порядок входят в одну `photos.mutate/form`. Новых файлов нет. Смешанное удаление
с перестановкой, новые вложения с удалением, размещение, копии и admin пока
остаются отдельными открытыми направлениями.

- UUID фиксируется один раз до первого ожидания. SELECT-only `photo-owner-state`
  должен подтвердить исходную версию списка, весь payload владельца и отдельные
  версии каждого фото. Более новая карточка не подменяет версию фотографии.
- Полное намерение и итоговый снимок пишутся до обновления UI. `fileIntentHash`
  равен `null`; чтения/записи новых файлов и staging нет. Отдельный
  `PERSONAL_PHOTO_EDIT_FORM_ENABLED = false` ограждает capture и dispatch.
- Quota, смена контекста или неподтверждённая база сохраняют полную форму для
  диагностики. Повтор той же сессии не получает новый UUID.
- После lost ACK восстанавливается прежняя точная квитанция. Неизвестный
  результат не разрешает новый POST. После принятой квитанции читается свежая
  серверная версия, а не применяется исторический снимок.
- Явная отмена проверяет/отменяет прежний owner ID без вызовов stage. Отложенный
  выбор сохраняет исходную форму. «Оставить серверную версию» создаёт отдельное
  проверяемое действие; отменённая форма никогда не отправляется как новое.

## Проверки и обнаруженные ошибки

- Frontend: 415/415 transport (включая 10 новых unit), 892/892 critical,
  source check и проверка diff. UI-пакет: 28/28 — normal/lost ACK, reload,
  неизвестный результат, quota, устаревший владелец, отмена и отложенный выбор.
- API: 105/105 настоящих MySQL/HTTP, 61,16 с; 41/41 operation и 74/74
  source/service. Четыре сочетания item/container × delete/order используют
  настоящие frontend session/outbox/queue/drain и transport. Нативное браузерное
  хранилище проверяется отдельно, API-стенд использует тестовый storage.
- В каждом новом API-сценарии: поле владельца меняется после прикрепления двух
  фото; версии 3 и 2 проверяются раздельно. Обрыв после COMMIT → закрытый GET →
  restart → неизвестный исход → точный GET, без второго POST и без staging.
  Затем отдельная форма отменяется с потерей ACK и рестартом, выбор откладывается,
  затем принимается новая серверная версия. Старый form после удаления владельца
  не меняет сырые таблицы; tombstone сохраняет версию 6.
- Две ошибки новой SQL-фикстуры исправлены: для правки удалённого существующего
  владельца ожидается `photo_owner_missing`, а не код попытки создать его снова;
  ключи сырых таблиц — `item_id`/`container_id`, не `id`. Проверки неизменности
  строк, подтверждений и tombstone сохранены.
- Исходный mobile WebKit сбой воспроизведён на пятом повторе: кнопка получила
  `pointerdown`, `mousedown`, `mouseup`, но **не click**. Действие выбора главного
  фото не выполнялось. Мобильный сценарий использует `tap` и отдельно проверяет
  click и новый порядок превью до SAVE. Нет повторного нажатия до успеха,
  принудительного DOM-click или ослабления проверки action/form.
- Следующий UI-прогон: 21 passed, 1 failed, 6 не запускались. Все business/receipt
  утверждения упавшего lost-ACK сценария прошли; ошибка была в учёте отменённого
  `/auth/me` во время намеренного reload. Трасса: начало reload 408093 мс,
  WebKit pageError 408143 мс. Шаг подключён к существующему reload helper с
  ожиданием окна восстановления; общий фильтр ошибок не расширялся.
- Отдельный API-прогон остановлен `listen EACCES` на временном порту 55227.
  Локальный Windows диапазон исходящих портов: 49152–65535. Теперь начальный
  выбор тестового listener использует свободный 20000–29999, а остановка ждёт
  exit даже после принудительного завершения. Перезапуск и POST не повторяются
  автоматически. Возможная конкуренция за временный порт — объяснение, а не
  доказанная причина прежнего native crash Node с кодом 3221226505; тот вопрос
  остаётся открытым. Два последующих API-прогона прошли 105/105.
