# Отдельная копия вещи в выбранную сумку

Локальное продолжение 2026-09-08. Путь проверен локально; API `aab9df3`.
Публикация отложена пользователем; рабочие флаги выключены.

## Реальная кнопка

«Скопировать в другую укладку» сначала связывает существующую вещь с целью.
Если вещь уже есть в выбранной укладке, приложение предлагает отдельную копию.
Личный обработчик теперь готовится до этого подтверждения: фиксирует полный
источник, целевую укладку/сумку, ID операции и все новые ID. Данные записываются
в журнал до появления копии и переключения интерфейса. Изменившийся редактор
не применяет прежний выбор. Публичные и административные пути остаются отдельными.

В UI доступны другие укладки; сохранена эта политика. Внутри обработчика
проверен и вариант той же укладки. Целью может быть корневая сумка или карман.
Копия получает каталожное количество исходной вещи; количество и packed прежних
размещений не меняются, новая копия не отмечается упакованной.

## Данные действия

Без фото применяется обычный `list.update` с полным неизменяемым payload и
`userItemCopyPlacement` (version/type/sourceId/targetId/targetLayoutId/
targetContainerId). Сверка с другой локальной или серверной версией удаляет
маркер исходного копирования из нового действия, сохраняя выбранные данные.

С фото используется прежний fileless `photos.mutate/action: copy-batch`,
ровно один владелец-вещь, с необязательным строгим `copyPlacement`:

```json
{
  "version": 1,
  "targetLayout": "полная выбранная укладка",
  "targetContainerId": "выбранная сумка",
  "targetIndex": null,
  "layoutFields": {}
}
```

`targetLayout` в запросе — объект, а не строка из поясняющего примера.
`copyTree` и `copyPlacement` одновременно запрещены. Полный target-граф
проверяется на циклы, пропуски/дубли, порядок, родителей, количества, packed,
личную область и блокировку. Компилятор ничего не нормализует и не чинит.
На сервере source owner и его numeric revision проверяются SELECT-only;
полная цель сравнивается под list CAS до любой бизнес-записи. Новая вещь,
фото/asset-ссылки, размещение, история и receipt фиксируются одной транзакцией.
Подтверждённые физические файлы повторно не загружаются.

Receipt содержит `photoCopyPlacement` с version/itemId/targetLayoutId/
targetContainerId; клиент проверяет всю целевую укладку, владельца, новые фото
и допустимые производные placement-поля. Старый body/hash не меняются при
восстановлении или повторном чтении receipt.

Удаление до ACK использует полный прежний `photoResults.version: 2` и
зависимости от оригинальной копии и непосредственного предшественника.
Удаление источника, копии или целевой сумки проверяется отдельно. При удалении
сумки скопированная вещь остаётся в каталоге без размещения.

## Флаги и проверки

- `PERSONAL_PHOTO_COPY_PLACEMENT_ENABLED = false`.
- API `BIKE_PACKING_CAUSAL_PHOTO_COPY_PLACEMENT_ENABLED` unset; зависит от всех
  прежних photo/form/copy/batch gates. Capability `personalCausalPhotoCopyPlacementV1`.
- Локальные prepare/outbox/dispatch/cancellation и серверный gateway/handler
  проверяют соответствующий флаг. Isolated UI bundle включает его только для тестов.
- `personal-photo-copy-placement-layout.js` зеркалируется в API byte-for-byte.
- Первые unit/API-ошибки в тестах: использован recover вместо list; некорректный
  pending-photo fixture; SQL id вместо item_id/container_id; серверный UI-mirror
  packedItems не согласован с authoritative arrangement. Проверки не ослаблялись.
- Первый UI fixture ошибочно ожидал текущее назначение в кнопке, которая
  исключает исходную укладку. Он заменён двумя реальными целями: сумка/карман.

Это отдельный проверенный путь, а не завершение разделов 06/07
или всего перехода. Следующий обнаруженный вопрос общего пути: старые личные
DB-адаптеры ещё применяют кандидат к памяти до сохранения в журнал.
