# New photos in an existing administrative template

Local first-slice checkpoint, 2026-09-11. The final runtime passed **28/28** actual photo browser scenarios, **8/8** neighboring-copy regressions, **1455/1455** transport tests, source checks and the default-OFF build. Both browser runs covered Chromium and mobile WebKit without retries or skips. This checkpoint completes the bounded first append slice; the remaining administrative file operations and overall migration acceptance stay open.

## Supported first slice

An administrator can append 1–50 new photographs to **one existing item or container** in an existing, confirmed, private demo/shared template. The same form may save its ordinary supported fields: name, weight, color, location, categories, note, dimensions, edit metadata, and the applicable item/container fields. Existing photographs, their full raw metadata and their order remain unchanged. An existing owner with no photographs can receive its first photograph when its exact server identity is proven.

The form requires the observed numeric source revision, its exact source snapshot, and the complete local-to-server owner map captured during materialization. It rejects a pending source/base, a pending copy or another unresolved save, public templates, owner creation, placement/availability/catalog-source changes, deletion, replacement or reordering of old photos, mixed owners, ZIP import, and publication.

Each original file and optional thumbnail must be a supported image and no larger than 10 MiB; the frontend package is capped at 50 MiB in total. Preview cache entries alone cannot supply upload authority or replace the retained original bytes.

## Frozen action, bytes and plans

The actual item/container form controller retains the original Blob handles before asynchronous preview-cache work. Save captures the full selected photos and form fields into one immutable input. After validating the source and current owner mapping, `adminTemplatePhotoFormPayload` clones the **complete exact raw source** and changes only the selected server owner's permitted form fields. A null dimensions value deletes that field. Old raw photo references, other owners, layouts, arrangements and packed maps, dictionaries, and unknown fields remain exact. This file action does not use the ordinary full export to reconstruct its payload or temporarily mutate the live owner.

The record validator independently compares the complete raw source and action payload, permitting only those selected-owner form fields to differ. Changed field values must agree with the frozen editor; the old photos and all other raw data remain unchanged. A fresh inventory hash cannot authorize normalization loss or a substituted payload during cold recovery. This correction is limited to the new-photo form; it does not redefine every legacy export path.

The app retains the save UUID for the immutable form input. `prepareAdminTemplatePhotoRecord` creates its bound stage manifests and digests before any stage request. Each manifest binds environment, actor, stage UUID, save UUID, target key/list, source revision, existing owner type/ID, photo ID, and original file/thumbnail metadata and byte hashes. `assetDigest` is the canonical manifest hash; server image normalization does not redefine it.

The separate administrative IndexedDB inventory retains the full action, source snapshot, pending editor snapshot, optional exact `beforeState`, all manifests, and complete file bytes. Both capture and read-back validate hashes and structure. The `beforeState` comparison permits only the chosen owner's supported form fields and appended photos to change; an explicitly malformed or null `beforeState` is rejected. Personal file journals and authorization checks are not reused with an administrative bypass.

The administrative save plan is **version 5**. Its operation is a confirmed-base `template.save` with `photoAppend.assets`; `body.payload` contains old photo references only. Its separate editor snapshot contains the pending local photos and form fields. The file inventory, plan and client action are durable before the form closes or a stage upload begins. Local `photoAppendPending`/plan markers allow the same action to be recovered after reload.

## Server attachment and authoritative result

`POST /bike-packing/admin/template-photo-assets` stages the exact multipart manifest and bytes; its GET route returns the immutable stage receipt or an explicit unknown result. Stage alone does not modify the template, photograph rows, publication heads or history. Duplicate multipart parts and unrecognized fields are rejected.

After every stage is verified ready, the client persists those receipts before posting the original save. Under the administrative catalog/list/owner locks, the backend verifies current rights, exact source revision, unchanged existing owners and photos, stage-to-save bindings, and actual staged bytes. It attaches the new photo rows/references, writes history, advances the head and stores the immutable result in one transaction. An oversized result, crash or late authorization failure rolls back the effects.

The administrator/uploader may differ from the template owner. New photo rows belong to the locked template owner; new publication heads identify the uploader. Existing owners, photo rows and heads keep their previous identities and metadata. Personal owner checks are unchanged.

The successful receipt contains ordered added references and the authoritative full `confirmedPayload` plus its digest. The client verifies the operation identity, stage proofs, target owner IDs, unchanged old prefixes, ordered additions and full payload hash before adopting the accepted version. It never reconstructs that accepted snapshot by reading a potentially newer current version. Lost responses and replay retain the original UUID and receipt; a second attachment is not created.

The raw submitted payload and accepted receipt retain opaque source fields exactly. The working UI uses the existing normalized representation and may omit opaque fields that it does not display. That normalized view is not the authority for reconstructing the accepted raw payload; supported form fields, owner identities, photographs and arrangement/packed state still have to survive projection and recovery.

## Quota, retries and recovery

- A pre-durable synchronous or asynchronous failure releases the form's busy state. A repeated Save passes the **same input object and callback options** to the submitter; it does not reread a changed form. The app caches the save UUID and completed record by that input, preserving identifiers and bytes across an uncertain capture. Changed form/account/editor context stops the attempt and retains the original recovery material.
- The candidate and confirmed-result UI mirrors use a strict write/read-back path. They do not evict private baseline or recovery records to make space. A failed mirror leaves the durable inventory/action available for recovery. With an owned administrative editor present, the ordinary snapshot, base and recovery writers also disable quota cleanup that would evict a baseline or recovery history. In particular, a failed recovery-history append cannot delete the retained history and retry with only the newest entry. Successful personal snapshot/base/recovery writes remain allowed; this is a quota-fallback constraint, not a blanket ban on personal persistence.
- IndexedDB checks existing actions and inserts the new record in one serialized transaction. A different save UUID for the same target binding and source revision is rejected; another tab cannot silently create a second package for that base. The same immutable record can be read back or recaptured.
- Recovery discovers an inventory orphan left before plan/client/UI-marker persistence, restores only an exact matching before/candidate editor, and continues the original action. Missing, conflicting or multiple candidate records stop for reconciliation; timestamps and UUID order do not choose a winner.
- Cold loading, loaded-state application and state replacement preserve the exact stored administrative photo-editor namespace before general personal-state normalization. This includes detached items/containers, old photo views and the source/owner-map markers. Recovery still compares the complete before/candidate business snapshot; it does not ignore added defaults or accept a changed source. Form dimensions with a null value remove that field, matching the ordinary form semantics.
- The individual and bulk legacy draft-solidification wrappers leave current-account causal photo editors' recorded arrangements intact, including while a private layout is active. A personal save cannot reconstruct an inactive administrative template's packed state from the active private view. Ordinary legacy drafts and the feature-OFF behavior retain their existing repair path.
- An unknown stage remains paused and is not uploaded again, including after reload or loss of the transport journal; its durable IDB dispatch claim survives. A verified stage receipt with missing/corrupted bytes remains unavailable.
- Cancellation may pass only the original save's exact unknown stages on its exact cancel URL. The temporary transport permission binds action UUID, payload digest and asset UUID/digest to the retained actor/environment/target metadata. Cancellation neither acknowledges nor removes an unknown stage. Ordinary save and unrelated writes remain fenced by that uncertainty.

Ordinary export also preserves the recorded server IDs of existing empty-photo owners, avoiding an implicit ID-prefix change before their first photograph. After an ordinary confirmed field save, source preparation may read the server only when its returned revision is **exactly** the editor's observed base. Existing mappings and raw photo references must still validate. This is not a rebase: a newer revision or an unproven owner mapping stops the operation. The final browser suite covered the ordinary-save-to-photo path in both engines, including an empty-photo owner whose server ID lacks an export prefix.
