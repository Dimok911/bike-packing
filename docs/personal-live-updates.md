# Быстрое обновление открытых страниц

Кандидат v1622 основан на опубликованном v1621. Пользователь подтвердил на
телефоне восстановление, быструю загрузку и обмен после ручного обновления.
Этот небольшой следующий этап добавляет уведомления о новых версиях.

Сервер после успешного ответа на изменение будит подписчиков. Для каждого
соединения заново проверяются сессия, доступ к списку и его текущая ревизия.
Только изменившийся доступный список даёт событие SSE `changed` с пустым
объектом. Подключение даёт `ready`, чтобы проверить изменения, пропущенные
во время разрыва. Это подсказки для чтения, а не подтверждения операций.

Клиент использует выбранный проверенный маршрут и прежнюю сессию. Поток
читается через fetch с запретом перенаправлений. Уведомления вызывают
существующую проверку freshness → changes → при необходимости полный снимок.
Местные неподтверждённые действия, выполняющееся сохранение и смена аккаунта
блокируют применение. После сохранения отложенная подсказка проверяется снова.
Сигнал никогда не записывает данные сам и не меняет индикатор сохранения.

Скрытая вкладка, офлайн, выход из аккаунта и уход страницы в кеш браузера
закрывают соединение. Возврат открывает его заново. Проверка каждые 30 секунд
остаётся запасным способом. Без серверной возможности `listLiveUpdatesV1`
поведение прежнее. В первой версии подписки обслуживают личный список аккаунта;
публичные страницы/редактор шаблонов в эту подписку не включены.

Серверный флаг: `BIKE_PACKING_LIVE_UPDATES_ENABLED=1` только в Experiment.
Уведомления в памяти рассчитаны на нынешний один процесс API; сервер проверяет
ревизии также каждые 20 секунд. Соединение ограничено 55 секундами для корректного
завершения старых Nginx workers при публикации. Максимум 128 соединений; при
превышении лимита клиент продолжает периодические проверки. Медленный клиент
закрывается, без накопления очереди сообщений. Горизонтальное масштабирование
потребует общего канала уведомлений, но не изменения формата сохранения.

Для двух прокси RU передаёт `X-Accel-Buffering: no` дальше через
`proxy_pass_header X-Accel-Buffering`, иначе Frankfurt может задерживать SSE.
Это отдельная настройка экспериментального маршрута, не изменение Auth.

Проверки: реальный HTTP с двумя подписчиками и проверкой изоляции; реальная
MySQL/каноническая авторизация/старое PUT и подтверждаемая операция; браузерный
тест собранного приложения в Chromium и мобильном WebKit; отложенная проверка
местных правок и смена контекста. Приёмка на физическом телефоне после публикации:
оставить страницу открытой, изменить название на компьютере, дождаться обновления
без перезагрузки; повторить на европейском API и после возврата из фона.
