# Минимальное переносимое ядро: разработка завершена

15 сентября 2026. Карточка https://trello.com/c/6B3JbblM.
Статус: разработка готова локально; публикация и пользовательская приёмка
на физическом телефоне для этого кандидата ещё не выполнены.

## Результат

Один общий модуль обслуживает переименование личной вещи Bike Packing
и переименование заметки в независимом HTTP-примере. Извлечены идентичность
операции, канонизация, договор хранения намерения/квитанции, доставка и
возобновление. В ядре нет импортов Bike Packing и правил вещей, фото,
авторизации, DOM, localStorage или конкретной БД.

Вход модуля и договор адаптеров: `src/protocol/index.js`,
`src/protocol/README.md`. Независимый пример: `examples/confirmed-notes`.

Bike Packing использует прежние UUID, list.update, payload, hash, ключи
журналов, Web Locks, capability checks, отмену и waiting/prepared recovery.
Подтверждение сохраняется и перечитывается до успешного возврата. Ошибка
хранилища, чужая квитанция или иной payload с тем же ID не дают ложного
успеха. Unknown сам по себе не разрешает повторную отправку.

Серверный адаптер сохраняет действующий транзакционный журнал. Разработка
универсального SQL-сервера не понадобилась для первого переносимого ядра:
совместимость доказана с настоящим серверным кодом выпуска v1622 и MySQL.
Пример заметок использует собственный файловый серверный адаптер. Его
ограничения (один процесс, отсутствие производственной авторизации и
гарантий при отключении питания) описаны рядом с примером.

## Проверки окончательного кода

- 132 целевых проверки: ядро, очередь операций, подготовка повтора,
  восстановление обычных сохранений. Все прошли, пропусков нет; ~1,9 с.
- Обычная Vite-сборка с подготовкой статических файлов — прошла. Существующее
  предупреждение о размере чанков остаётся; оптимизация загрузки не входит
  в этот шаг.
- 4 проверки собранного интерфейса: Chromium и mobile WebKit, обычное
  переименование и потеря ACK с холодным восстановлением. Все прошли;
  ~21,6 с. API в этих браузерных сценариях изолированный синтетический.
- 5 выбранных узлов настоящего HTTP/MySQL smoke прошли, включая корневой
  тест: CRUD/receipt/replay/ownership, COMMIT faults, текущая клиентская
  очередь с семью видами команд и отдельное переименование с reconciliation,
  потерей ACK и восстановлением outbox. Реальные Node API и MySQL работают
  только на loopback; ~7,4 с непосредственно тестов.
- Независимый HTTP-пример: committed после потери ответа и после
  перезапуска клиента/сервера, тот же ID, серверный эффект ровно один.
- Независимый ограниченный просмотр трёх модулей ядра и diff адаптера
  не выявил конкретных регрессий. `git diff --check` прошёл.

## Настоящая БД и воспроизводимость

Команда: `scripts/test-protocol-core-with-local-mysql.ps1 -NodeExecutable <node.exe>`.
Wrapper использует переносимую MySQL из root cache, новый datadir, проверяет
его фактический путь до работы с БД, затем закрывает процессы. Данные
успешного запуска сохранены в root cache:
`node_modules/.cache/mysql-causal-test/protocol-core-run-604816fb2d6943c588edf9e9c18c7400`.

API-клон: соседний `protocol-core-api-v1622`, исходный runtime commit
`a2716d28b1e5bdb476a8463cfd4efcb9a404fed5`. Изменён только тестовый harness:
нынешний canonical Experiment URL сопоставляется с настоящим loopback API,
а scope protocol-core завершается после выбранного paired сценария через
существующий finally. Runtime сервера, схема БД и опубликованный клон
не менялись. Зависимости API повторно используются из уже установленного
node_modules опубликованного клона через локальную junction.

Ранние попытки узкого запуска выявили ошибки настройки harness: логи
делали datadir непустым, фильтр пропускал служебный узел Node, старый URL
и общий tail зависели от других тестов, новой копии не хватало зависимостей.
Это исправлено; ни один неполный/пропущенный запуск не засчитан как приёмка.
Полная фото/импорт матрица и GitHub Actions не запускались.

## Что считается завершённым и что не обещано

Разработка первого переносимого ядра и его подключение к двум приложениям
завершены. Публикация пакета в npm, перенос всех предметных обработчиков,
фотографии/импорты из остатка перехода, частичная загрузка и расширение
офлайн-режима не являются скрытым продолжением этой карточки.

Кандидат построен от опубликованного frontend v1622 в отдельной ветке
`codex/protocol-core-v1622`. В эксперименте по-прежнему опубликована v1622;
Production не менялся. Следующий этап этого результата — публикация в
Experiment и короткая проверка на телефоне: переименовать вещь, увидеть её
на втором устройстве, повторить после временного отсутствия сети. До
этого карточка относится к «Разработка готова», а не к «Принято».
