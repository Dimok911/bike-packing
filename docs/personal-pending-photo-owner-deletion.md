# Удаление владельца во время загрузки фото — локальный этап 2026-09-08

Обычная кнопка удаления вещи/сумки теперь может зарегистрировать удаление за
точно сохранённой фотоформой. Сначала создаётся один UUID и весь снимок удаления
записывается в outbox; только затем меняется экран. Исходная форма, её UUID,
новые photo/asset IDs, файлы и состав запроса остаются неизменными.

`PERSONAL_PENDING_PHOTO_OWNER_DELETION_ENABLED = false` — отдельное ограничение
поверх существующего пилота удаления владельцев и фотоформ. Сопоставляется вся
исходная форма, а не наличие произвольной pending-ссылки. Результат явного
удаления должен убрать именно её владельца; фото оставшихся записей сохраняются
точно. Проверяется каждый последующий шаг цепочки, включая запрет возвращения
удалённого владельца без фотографий. Историческая ссылка checkpoint не является
активной зависимостью.

Диспетчер сначала устанавливает точный результат файлов/формы и лишь затем
отправляет удаление с `causal.baseOperationId` этой формы. Уже подтверждённая
форма проверяется через GET без повторной загрузки. Старый обработчик, который
ждал файл в момент нового удаления, прекращает работу; продолжает обработчик
новой цепочки. В интерфейс не устанавливается исторический снимок фотоформы.
После reload доступно явное продолжение всей сохранённой цепочки.

Отдельная отмена сначала получает серверный запрет применения исходной формы,
затем проверяет/отменяет её точные стадии. Зависимое удаление получает точное
`dependency_rejected`. Выбор «оставить серверную версию» — отдельное действие;
отложенный выбор сохраняет всю очередь и все файлы.

Для отмены собственной формы допускается собственная неподтверждённая стадия
файла: локальная transport-запись помечается `cancellationOnly`. Совпадают список,
аккаунт, исходный form UUID, владелец, фото и asset ID из замороженного manifest.
Такая запись запрещает отправку бизнес-сохранения, включая восстановление из
`waiting`. Чужие и обычные неподтверждённые записи сохраняют прежний запрет.
Это внутренний признак журнала, не разрешение из HTTP-параметра.

## Проверки и диагностика

- 16/16 обычных UI-сценариев Chromium/mobile WebKit, 4,2 минуты без повторов:
  новые/существующие владельцы, файл в полёте, потерянный ACK формы/удаления,
  перезапуск и quota. Лог `pending-owner-ui.log`.
- Дополнительный UI-пакет отмены и отложенного выбора — 8/8 Chromium/mobile
  WebKit, 3,2 минуты без повторов; `pending-owner-cancel-ui-4.log`.
- 435/435 transport, 895/895 critical и source check.
- 115/115 настоящий API/MySQL, 89,41 с, без пропусков. Обратная доставка,
  COMMIT ACK loss, restart, точные tombstones и отсутствие повторных POST.
  Лог `pending-owner-cancel-mysql-3.log`, backend `6c90cf1` (проверки и документ).

Первые проверки отмены обнаружили два пробела: terminalization не принимала
отклонённую фотоформу как предшественника, а неизвестный результат собственной
загрузки блокировал даже её отмену. Оба исправления имеют отдельные проверки
точных зависимостей, отключённых флагов, чужих стадий и запрета повторного SAVE.
Отдельный сбой UI-фикстуры скрывал квитанцию ещё до самой отмены, вместо потери
ответа после неё. Инъекция перенесена после принятия cancellation POST;
требования к подтверждениям не ослаблялись.

Логи находятся в `node_modules/.cache/causal-evidence/2026-09-08/`.
Файлы не очищаются автоматически. Публикация отложена пользователем; push,
deployment, live-миграции и включение рабочих флагов не выполняются.
Копирование записей/деревьев с фото, архивы, обмен и административные действия
остаются отдельной работой. Раздел 06 и весь список перехода не закрыты.
