## Состав действия

Одиночная копия личной вещи или корневой сумки вне укладки — одна
`photos.mutate`, `action: form`, с созданием владельца (`baseEntityRevision: 0`)
и обязательными дочерними `copy`. Пустая промежуточная запись не публикуется.
Все поля источника сохраняются, включая неизвестные дополнительные поля;
меняются ID, название копии, метаданные редактирования и размещение.

`copySource` содержит точную запись источника, его личный список, тип, ID и
числовую версию. Каждый дочерний элемент содержит выбранные исходные
photoId/assetId/photoRevision, новые photoId/assetId и порядок. Частичный набор,
перемешивание attach/delete/order с копированием, другой список или подмена
полей через `fields` запрещены. Копия публичного/административного источника
требует своего отдельного адаптера.

`session.prepare()` синхронно фиксирует выбор и все ID до окна подтверждения.
`submit()` проверяет сохранённую очередь, затем читает версии источника через
SELECT-only `photo-owner-state`. GET может подтвердить замороженный источник,
но не заменить его новыми полями. Повторный submit использует тот же promise
и ID, в том числе после ошибки. Проверочный локальный preview с условными
версиями не является операцией и никогда не отправляется.

Только после сохранения полного fileless action в журнале меняется экран.
Quota или изменение источника оставляет прежний экран и выбранную копию для
выгрузки через восстановление. Обычные кнопки копирования ожидают эту запись
перед сообщением об успехе. Текущий показ фото не является полномочием на
повторную загрузку или регистрацию нового действия.

## Сервер и восстановление

Под блокировкой списка API проверяет точную строку и версию источника, все
публикации фото и наличие сохранённых байтов. Копия получает свои строки,
photoId и assetId; физические неизменяемые файлы и превью используются повторно.
Ни HTTP staging, ни запись/удаление файлов для обычной копии не нужны.
Владелец, производные assets, строки фото, история и квитанция сохраняются
одной транзакцией; ошибка второго фото откатывает и первое.

Собранное представление списка содержит вычисляемое размещение активной
укладки. Оно сравнивается с записью каталога после удаления только этих
зеркальных полей. SQL-строка источника по-прежнему сравнивается полностью,
без нормализации и без ослабления числовой проверки версии.

Квитанция проверяет весь состав копии, ID, порядок и метаданные каждого фото.
URL нового фото возвращает сервер; клиент их не угадывает. Потеря ответа
разрешается по старому ID через GET. Старый результат не становится текущим
экраном: после подтверждения читается актуальный личный список. Удаление
источника после принятой копии не удаляет её фотографии и не оживляет источник
при повторном чтении прежней квитанции.

Fileless копия распознаётся при перезагрузке даже с выключенным writer gate.
Явная отмена фиксирует прежний ID без загрузок; выбор «оставить серверную
версию» является отдельным действием. Отложенный выбор сохраняет исходную
копию и очередь.

## Границы текущего участка

- Это одиночное копирование в каталоге без помещения копии в укладку.
- Массовое копирование с фото, дерево сумок и копия всей укладки ещё открыты.

  следующего адаптера. Его нельзя подменить сохранением pending-ссылок как
  подтверждённых фотографий либо подбором URL по текущему источнику.
