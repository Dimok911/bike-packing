# Ядро протокола / Protocol Core

Архитектурный срез на **17 сентября 2026 года**. Это описание проверенного кода, а не обещание завершённого перехода всего приложения. Поведение протокола при подготовке документа не менялось.

## 1. Область проверки и значение слова «ядро»

Проверены документация checkpoint, migration review, first slice, acceptance, договор `src/protocol/README.md`, компактные операции и фактические вызовы в коде:

- **FE:** `node_modules/.cache/experiment-whole-copy-v1627`, runtime `506d9fbf9f0ea27c494fd11cfaca3e1843b112d2` (v1630). Коммит `1e35b469` после него меняет только проверку схемы при выпуске.
- **API:** `node_modules/.cache/whole-copy-release-api-v1627`, runtime `094a1c1d1fbd333842e5792d5d8896e7df200e37`.
- В корневом рабочем дереве ещё нет `src/protocol`; оно содержит более старый код и незавершённые правки. Нельзя смешивать его с указанным выпуском. Ссылки ниже закреплены на проверенных коммитах.

Нужно различать **архитектурный договор Protocol Core** и **уже выделенный переносимый модуль**. Договор требует устойчивой идентичности, доказуемых предусловий, зависимостей, идемпотентности, согласованной фиксации и безопасного восстановления. Сейчас этот договор обеспечивается совместной работой небольшого клиентского ядра и адаптеров Bike Packing; не все его части универсальны и не все действия приложения подключены.

Фактический переносимый модуль — четыре файла `src/protocol`: `operation-identity.js`, `operation-journal.js`, `confirmed-delivery.js`, `index.js`. В нём **нет** общего планировщика зависимостей, CAS/rebase, проверки предметных ссылок, SQL-исполнителя или менеджера файловых стадий. Это не недостаток, который следует исправлять переносом таблиц Bike Packing внутрь Core: общими должны становиться договоры и механизмы, предметные правила остаются снаружи.

Исторические документы «ядро завершено» относятся к этому минимальному модулю и двум интеграциям. Они не означают завершение всех девяти гарантий для каждого маршрута приложения. [Первый договор модуля][core-readme]

## 2. Фактические уровни и границы

```text
Личная правка UI
  → personal-save-outbox / list-operation-queue (план, очередь, допуск)
  → src/protocol (identity, journal, confirmed delivery)
  → адаптер транспорта / API / проверка предметной операции
  → серверный журнал + транзакция MySQL
  → проверка receipt / свежести → локальное сохранение и UI

Административный whole-copy UI
  → сохранённый typed plan + общий допуск/блокировки
  → собственный whole-copy client (НЕ createConfirmedDelivery)
  → stages фотографий → parent template operation
  → предметные проверки + транзакционный template journal
  → собственная проверка receipt / применение / восстановление
```

Проверки располагаются и до отправки, и внутри серверной транзакции; это не один последовательный фильтр `Core → validation`. Клиентские проверки не заменяют серверные.

| Уровень | Ответственность | Чего ему нельзя приписывать |
|---|---|---|
| Переносимый `src/protocol` | Сравнение идентичности; канонизация; договор записи/контрольного чтения; последовательность доставки и восстановления | Знание вещей, фото, revision, прав, БД, браузера, UI |
| Адаптер приложения/очереди | UUID и digest; durable storage; блокировки; контекст аккаунта; зависимости; возможности сервера; проверка receipt и свежести | Право считать HTTP 200 достаточным подтверждением или перепосылать `unknown` |
| Предметная операция | Применимость к конкретным объектам, ссылки, допустимые конфликты/слияние, узкие legacy-правила | Право подменять исходную команду под прежним ID или обходить журнал |
| Серверный адаптер хранения | Аутентификация; уникальный scoped ID; блокировки; транзакция эффекта/receipt; чтение результата | Общая атомарность произвольных файловых/внешних эффектов только из-за SQL COMMIT |
| UI | Показ состояния и осмысленный выбор пользователя | Доказательство сохранения, принудительное обнуление неподтверждённой очереди |

Независимый `examples/confirmed-notes` действительно импортирует те же функции ядра. У него собственные HTTP/файловый адаптер и receipt. Он доказывает переносимость этих функций, **не** универсальную многопользовательскую причинность: один процесс, без производственной авторизации и без заявленной гарантии при отключении питания. [Код примера][notes]

## 3. Матрица девяти принципов

**Реализовано** — механизм есть в переносимом ядре, при выполнении явно указанного договора адаптеров. **Частично** — часть механизма общая либо гарантия обеспечена отдельными адаптерами/семействами операций. **Целевое** — общей реализации ещё нет. Ни один статус не означает автоматический охват legacy/production-маршрутов.

| № | Принцип | Статус | Фактическая граница |
|---|---|---|---|
| 1 | Устойчивая идентичность | **Реализовано** в договоре Core | Сравниваются шесть полей идентичности; журнал проверяет неизменность записи. Генерация UUID, атомарная уникальность и серверная защита — обязанности адаптеров (§4). |
| 2 | Причинный порядок и зависимости | **Частично** | Личная очередь и отдельные server dependencies реализованы. Универсальный граф всех UI-действий и устройств — **целевое** (§5). |
| 3 | Базовое состояние | **Частично** | Схемы и проверки revision/CAS есть в адаптерах; Core не интерпретирует revision. Правила отличаются у rename, list.update и whole-copy (§6). |
| 4 | Digest/hash-доказательства | **Частично** | Core канонизирует JSON и сравнивает строку digest; вычисление SHA-256, состав доказательств и проверка содержимого находятся в адаптерах (§7). |
| 5 | Идентичность сущностей и ссылки | **Частично** | Core проверяет идентичность операции; предметную целостность доказывают конкретные обработчики. Единого валидатора сущностей нет (§8). |
| 6 | Атомарность | **Частично** | Для защищённых серверных команд эффект и receipt в одной SQL-транзакции. Core сам транзакцией не владеет; файлы стадий имеют отдельную границу (§9). |
| 7 | Идемпотентность повторной доставки | **Частично** как общее свойство Core | Реализована журналами серверных адаптеров для подключённых команд. Единого серверного ядра и общей дедупликации всех маршрутов нет (§10). |
| 8 | Сверка неопределённого результата | **Реализовано** в механизме доставки Core | После ошибки — чтение того же ID; recover по умолчанию не отправляет. Семантику статусов/receipt и разрешение продолжения проверяет адаптер (§10). |
| 9 | Conflict / STOP вместо угадывания | **Частично** | Core отказывает при нарушении идентичности/записи/подтверждения; предметные STOP, конфликты и rebase реализованы вне него. Единой модели всех отказов нет (§11). |

## 4. Идентичность: что именно нельзя подменить

`matchesOperationIdentity` сравнивает `{ id, namespace, owner, resource, kind, digest }`: каждое ожидаемое поле — непустая строка и должно совпадать. Это проверка идентичности, не генератор уникальных ID и не валидатор схемы операции. [operation-identity.js][identity]

`createOperationJournal.capture` сначала проверяет отсутствие записи, вызывает `writeIntent`, затем перечитывает её, сравнивает идентичность и каноническое содержимое. `confirm` требует proof и совпадение его проекции идентичности, записывает подтверждение и перечитывает его. Ошибка этих шагов не даёт успешного завершения. [operation-journal.js][journal]

**Условие договора:** `writeIntent` обязан атомарно отказать при занятом ID, а вызывающий код — держать блокировку очереди. Само `find → write` не является межвкладочным CAS. Сам Core не пересчитывает digest записи и не проверяет подлинность произвольного proof: `identityOf`, схема и `accept` — доверенная часть адаптера, которую тоже необходимо проверять.

В Bike Packing клиент фиксирует UUID и неизменную команду до отправки. Сервер выводит пользователя из аутентификации и использует ключ `(environment, actor_id, operation_id)`. Совпавший ID с другим digest/kind/listId не становится новой операцией. Однако существуют **раздельные** журналы личных операций, административных операций и фотостадий: это не единое глобальное пространство SQL-уникальности. [Личная очередь][queue] · [Личный серверный журнал][list-store] · [Административный журнал][template-store]

## 5. Причинность и несколько устройств

Для зависимого действия B нужна сохранённая связь с A, а не просто более позднее время или новый UUID. В личной очереди предшественник сохраняется вместе с записью; компактная цепочка восстанавливается из базы/checkpoint. Отсутствующий предшественник, разрыв/цикл и смена binding не разрешают обычную отправку. Сервер проверяет заявленные зависимости и может оставить операцию в `waiting`, а не применить её без результата предшественника. [Personal outbox][outbox] · [Сервер зависимостей][list-ops]

`causal-action-journal.js` содержит более общий предметный граф писателей/читателей ресурсов: например, update A → copy B → delete A. **В проверенном FE нет production-import этого примитива**; наличие файла и его тестов не означает, что все формы используют такой граф. [Примитив причинного журнала][causal]

Web Locks/допуск упорядочивают работу вкладок данного браузера, не объединяют очереди разных устройств. Устройства сверяются по серверным revision, предусловиям и явно переданным зависимостям. Сервер не восстанавливает неотправленное намерение A на телефоне из того факта, что B позже создано на компьютере. Общего межустройственного графа намерений и порядка для всех семейств операций **нет**. Сервер проверяет до 32 явных зависимостей и запрещает самоссылки/дубликаты, но общего обнаружения многооперационных циклов в проверенном resolver нет: взаимное ожидание не гарантированно разрешается автоматически. [Resolver зависимостей][dependencies]

## 6. Исходное состояние и изменившийся сервер

| Операция | Реальное предусловие и реакция |
|---|---|
| Личное полное сохранение | Базовая revision/причинные условия проверяются серверным адаптером; неподходящая база не даёт молча заменить текущую версию. Сверка/rebase находятся в приложении. |
| `item.rename` | `body.baseStateRevision`, `itemId`, `expectedName`. Общая revision может вырасти из-за другой вещи; целевая вещь не должна измениться после базы, имя должно совпасть. Проверяется revision сущности, не только общая revision списка. |
| `whole-copy` | `source.base.stateRevision`, digest исходного payload, точные владельцы/ссылки; `target.base === null` означает доказуемое отсутствие новой цели, а не перезапись пустого списка. |

Core не знает, эквивалентны ли два состояния с одинаковой revision. Для операций, требующих точного содержимого, нужны дополнительные доказательства. Серверная квитанция подтверждает **историческую** операцию: до применения к экрану отдельно проверяются аккаунт, поколение редактора и актуальность серверного состояния. Rebase не является универсальной функцией Core; безопасный новый successor — новая команда, старый ID/тело не переписываются. [Compact rename][rename] · [Подготовка whole-copy][whole-parent] · [Личная очередь][queue]

## 7. Уровни digest: одинаковое имя не означает одинаковые данные

| Поле/доказательство | Что связывает в текущем коде |
|---|---|
| `identity.digest` | Переданная адаптером идентичность содержимого. Core сравнивает строку, алгоритм не навязывает. |
| Операционный `payloadDigest` / SQL `payload_digest` | Неизменный envelope/тело команды по правилам конкретного семейства. У личных и административных parent-команд Bike Packing это SHA-256 canonical JSON без ID команды. **Исключение:** `template_photo_assets.payload_digest` — digest manifest стадии, включающего её `operationId`. Это не обязательно hash всего каталога. |
| `source.payloadDigest` | Конкретный полный снимок источника, относительно которого подготовлена копия. Проверяется вместе с revision. |
| `referenceDigest` | Точная запись ссылки на выбранную фотографию в исходном владельце, включая её метаданные. Не hash файла. |
| `copyDigest` | Общий commitment whole-copy: source/target, родительская операция, метаданные и распределение новых ID. Связывает отдельные стадии с одной копией; производные assetDigest исключены из этого commitment. |
| `assetDigest` | Точный manifest отдельной фотостадии, включая связь с родительской копией. |
| `intentHash` / `recordIntentHash` | Сохранённая локальная typed-запись и связь её с журналом/claims; обнаруживает подмену локального плана. |
| `stored.file.hash`, `stored.thumb.hash`, `sourceStored` | Байты исходных и новых файлов, размеры/типы. |
| `materialization` с digest путей | Раздельные пути исходных и новых файлов. Дополнительно сервер сверяет физические file identity/inode и байты; один hash одинакового содержимого не доказывает независимость файлов. |
| `confirmedPayloadDigest` | Содержимое результата whole-copy, которое принимается клиентом. |

Назначение/канонизация всегда определяются схемой данного поля. Например, демонстрационный notes-адаптер использует собственный состав хешируемого намерения. Hash здесь — доказательство совпадения содержимого, **не** цифровая подпись и не замена аутентификации. [Whole-copy commitment/manifest][whole-protocol] · [Typed record][whole-record] · [Проверка файлов][whole-assets]

## 8. Сущности, ссылочная целостность и Tristan Ridley

Идентичность операции недостаточна: серверные обработчики отдельно проверяют listId/itemKey, аккаунт-владельца, entityType/entityId, photoId, ссылку в payload, SQL-строку, head/tombstone и выбранный файл. Разные операции имеют разные схемы и правила. Общий Core не понимает структуру каталога Bike Packing.

В случае Tristan реально было 33 выбранных фото, из них у 13 SQL-запись сохраняла исторический `entity_id`. Новая вещь/сумка ссылалась на прежнее фото. Это историческая принадлежность к **сущности**, а не разрешение сменить владельца аккаунта. В источнике всего 94 строки фото, включая не выбранные для этой копии.

Исправление локализовано в `lockTemplatePhotoWholeCopySource`, **не** в `src/protocol`. Условие совместимости: публичный источник, отсутствие publication head и `reference.assetId`; ссылка должна точно присутствовать в подтверждённом payload. Сохраняются проверки того же списка, account owner, entity type, непустого физического entity ID, согласованности item_id/entity_id, отсутствия удаления, revision/digest и файлов. При causal asset/head действует точное соответствие entity ID. Private-источник этого исключения не получает. [Точный guard][legacy-guard]

Это правило класса старых опубликованных ссылок, не специальное условие по названию Tristan. Оно позволяет **прочитать** старую фотографию и создать независимые файлы/новые привязки; не исправляет исходные ownership-строки, не разрешает изменение чужих файлов и не переносится автоматически на delete/update/обычный photo-copy.

`sourceProof` whole-copy сохраняет и повторно сравнивает все исходные SQL-строки; неизбранные исторические фото не обязаны исчезать ради копии. Целевая копия, напротив, проходит строгую проверку новых владельцев и полного набора её фото. [sourceProof / finish][whole-parent]

Архитектурный принцип: **обнаружить несогласованность → предметным валидатором доказать узкий legacy-случай → применить ровно эту совместимость; иначе STOP**. Сейчас обнаружение этого класса несогласованности выполняет серверный адаптер операции, а не универсальная функция Core. Документ не объявляет будущую схему уже реализованным центральным валидатором.

## 9. Атомарность и большие staged-операции

Для личной или административной серверной команды атомарная граница — изменение бизнес-данных, revision/head и терминальная квитанция в одной транзакции MySQL. Отказ откатывает бизнес-эффекты к SAVEPOINT, но может сохранить терминальный `rejected`. Это гарантия серверных адаптеров, не результат вызова `createConfirmedDelivery`. [Личные транзакции][list-store] · [Административные транзакции][template-store]

Для whole-copy имеются **несколько** атомарных шагов:

1. Каждая стадия с собственным ID подготавливает независимые файлы и сохраняет свой ready-receipt.
2. До parent COMMIT эти файлы не означают, что шаблон создан.
3. Родитель проверяет полный набор стадий, источник и отсутствие цели; создаёт целевой каталог, привязки фото, heads и итоговый receipt согласованно в своей транзакции.
4. Только точное подтверждение родителя и принятие его клиентом завершают логическую копию.

Файловая система не откатывается вместе с MySQL. При неопределённом результате могут остаться неподключённые файлы; catch не удаляет их наугад. Отмена не отменяет уже подтверждённое действие. Общего распределённого COMMIT/GC для любых внешних эффектов в Core нет; срок хранения подтверждений и безопасная очистка требуют отдельного договора. [stage/verify][whole-assets] · [prepare/attach/finish][whole-parent]

## 10. Повтор, unknown и восстановление

Типовой случай: сервер выполнил команду, ответ потерялся. Core вызывает `readReceipt` для **исходной** записи; `accept` адаптера проверяет её и сохраняет подтверждение. `recover` по умолчанию только читает. Один успешный HTTP-код не равен принятой команде. [confirmed-delivery.js][delivery]

Серверный повтор того же scoped ID и содержимого возвращает прежний терминальный receipt, не повторяя бизнес-эффект, **при сохранённых текущих правах доступа и разрешённом endpoint**. Отзыв прав может запретить чтение исторического результата; знание ID не заменяет авторизацию. Другие данные под этим ID отклоняются. Гарантия действует для соответствующего журнала, пока сохранена история; она не распространяется автоматически на иной endpoint, новый UUID или внешний сервис.

| Состояние/ответ | Значение и допустимое действие |
|---|---|
| `unknown` | Подтверждение не найдено/не установлено. Не доказательство отсутствия эффекта, не разрешение заново выполнить действие. |
| `waiting` и проверенный prepared-plan | Специальный путь личного адаптера: после проверки серверного разрешения, зависимостей и исходного намерения допускается продолжение того же ID. Не универсальный retry на HTTP-ошибку. |
| Готовая фотостадия / `assetState: ready` | Подтверждён один подготовительный результат, не весь шаблон. |
| `committed` | Исторически принят конкретный эффект. Для отображения текущего состояния нужна проверка свежести. |
| `rejected` | Достоверный отказ, а не успешное применение. Нельзя игнорировать его из-за внешнего HTTP 200. |

Core разрешает повторную отправку через `prepareRecovery` только согласно договору адаптера. **Сам модуль не проверяет криптографически/предметно это разрешение**: ошибочный hook с `beforeDispatch` может нарушить гарантию. Аналогично `accept` обязан понимать терминальные статусы — Core не имеет единого enum серверных состояний.

Кнопки «Проверить результат / Продолжить отправку» whole-copy реализованы собственным клиентом: перечитывают сохранённую typed-команду и этапы, проверяют binding/контекст, не выделяют новый UUID. Уже заявленная стадия с `unknown` останавливается; для неё нет общего автоматического blind retry. Восстановление первой старой стадии Tristan выполнялось служебно через аутентифицированный API с прежним manifest/UUID, после исправления и проверки причины; это **не** новая функция автоматического восстановления Core. [Whole-copy client][whole-client]

## 11. STOP, фактические пробелы и пути вне выделенного Core

STOP — описательный термин, не единый wire-статус. Core выбрасывает ошибки для чужой идентичности, изменённой записи, отсутствующего/несохранённого proof. Адаптеры добавляют stale revision, неизвестный исход, отсутствие прав/capability, неподтверждённые зависимости, конфликт фото и устаревший экран. Единых error taxonomy и conflict/rebase-механизма для всего приложения нет.

| Место | Что не обеспечивается универсальным Core | Как трактовать |
|---|---|---|
| `operation-journal.js` | Атомарность writeIntent и блокировка предоставляются извне; digest/proof проверяет адаптер | Договор доверенной интеграции; не самостоятельный безопасный storage engine |
| `confirmed-delivery.js` | Hooks accept/assertCurrent/prepareRecovery могут быть реализованы неверно; часть guards имеет пустые defaults | Нельзя подключить произвольный HTTP-клиент и автоматически получить все гарантии |
| `list-operation-queue.js` | Только этот основной queue-путь использует извлечённые journal/delivery; предметные проверки остались вокруг него | Переносимая часть реальна, охват не равен всему приложению |
| `causal-action-journal.js` | Примитив графа не подключён production-import ко всем формам | Универсальная причинность пока целевая |
| `admin-template-photo-whole-copy-client.js` и соседние admin-клиенты | Собственные журнал, claims, приём receipt, восстановление | Путь вне **модуля** Core, но не автоматически обход защиты: инварианты реализованы параллельно; есть риск расхождения реализаций |
| `api-client.js:46–109`: неподдержанный/выключенный queue-путь | Идёт через отдельный транспорт с его журналом/барьером, а не generic delivery | Не считать отсутствие импорта Core доказанным незащищённым обходом |
| `published-layout-save-flow.js:85–104`, `public-demo-template-admin.js:16–67`, старый history restore в `app.js:16627` | В исходниках сохранены прямые legacy-пути; их допуск и текущие release-флаги проверяются отдельно | `app.js:7439–7444` блокирует прямые Bike Packing mutations в активном личном пилоте. Само наличие этих функций не доказывает доступный обход, но app-wide exactly-once не заявляется |
| SQL-журналы разных семейств | Раздельная уникальность, зависимости и транзакционные исполнители | Нет общего сервера Core и автоматического порядка между всеми семействами |
| Фотостадии / quota / retained receipts | Файлы, лимиты браузера, срок жизни истории и очистка не решаются универсальным модулем | Требуют предметного хранения/восстановления; failure обязан оставаться явным |

Отдельно обнаруженный эксплуатационный пробел: предпубликационная проверка схемы ранее пропустила таблицы, которые whole-copy читает даже при выключенных функциях доступа. Он устранён в выпуске 3.3 отдельной проверкой схемы; это условие развёртывания адаптера, не новая гарантия Core. В рамках **этого документационного аудита** код не исправлялся.

Отсутствие общей реализации не доказывает потерю данных в конкретном пути. И наоборот, наличие защиты в одном whole-copy не доказывает её для всех create/update/delete/import. Данный аудит устанавливает границы перечисленных механизмов; полная приёмка всех кнопок остаётся отдельным объёмом.

## 12. Проверка следующего изменения

Для новой функциональности нужно явно ответить:

1. Где создаётся и долговечно фиксируется неизменная идентичность? Может ли после unknown возникнуть новый ID того же действия?
2. Какая связь B → A записана до отправки? Как сервер доказывает завершение A? Каковы границы аккаунта, устройства и семейства журнала?
3. Какие revision, expected values и digest необходимы именно этой операции? Что произойдёт при изменении сервера?
4. Где сервер повторно проверяет права, реальные ID/ссылки и отсутствие повторного использования цели?
5. Что фиксируется атомарно с receipt, какие внешние стадии остаются отдельно? Что означает частичный результат?
6. Кто проверяет receipt и свежесть перед обновлением экрана? Как восстанавливается исходная команда после потери ответа/перезапуска?
7. Если добавляется legacy-совместимость: каков точный predicate, какие доказательства обязательны, какие соседние случаи по-прежнему дают STOP?

Изменение общих механизмов не должно содержать имён шаблонов, исторических entity_id или правил «несовпадение можно проигнорировать». Предметное исключение допустимо только при сохранении проверяемого общего договора. Универсальность считается подтверждённой по реальным точкам интеграции и серверным гарантиям, а не по названию каталога Core.
