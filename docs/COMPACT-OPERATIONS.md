# Компактные операции: первый договор item.rename

16.09.2026. Готовы локально серверный обработчик и клиентский транспортный
адаптер. Обычная форма и личная офлайн-очередь ещё не переключены. Публикации
и включения флагов не было; Experiment остаётся v1625, Production — v1605.

## Production и целевой формат

Публичная сборка Production v1605 сверена: entity sync отправляет изменённые
вещи, сумки, укладки и справочники целыми записями. Для неподдержанных остаточных
изменений и восстановления сохраняется full-payload fallback. Переносимое ядро
не заменяет эти предметные обработчики; новые команды используют их и общий
транзакционный журнал подтверждений.

Первая команда POST /bike-packing/list-operations:

```json
{
  "environment": "bike-packing-experiment",
  "expectedActorId": "account-id",
  "operationId": "00000000-0000-4000-8000-000000000001",
  "kind": "item.rename",
  "listId": "personal-list",
  "body": {
    "version": 1,
    "itemId": "item-123",
    "expectedName": "Прежнее имя",
    "name": "Новое имя",
    "baseStateRevision": 17
  }
}
```

Тело ограничено 4096 байтами UTF-8; имена — 255 кодовых единиц. Payload и
флаги принудительной замены не допускаются. У команды обычные UUID, digest,
владелец и квитанция ядра. Сервер берёт владельца из сессии, не из команды.
Флаг сервера BIKE_PACKING_ITEM_RENAME_ENABLED=1 требует прежних Experiment/list
флагов. Capability personalItemRenameV1 появляется только при включении.
Клиентский PERSONAL_ITEM_RENAME_ENABLED пока false, адаптер требует capability.
Виртуальный путь клиента /lists/:id/items/rename отправляется только через
операционный gateway, отдельного незащищённого HTTP-обработчика нет.

Глобальная ревизия может увеличиться из-за другой вещи. Команда принимается,
если целевая вещь существует, принадлежит владельцу, не менялась после исходной
ревизии и её имя равно expectedName. Удаление/воссоздание с тем же ID не обходят
проверку. Изменение любого поля той же вещи пока консервативно считается
пересечением; независимость полей одной вещи не заявляется.

Используется существующий items.sync обработчик: история, общая ревизия и
уведомления сохраняются. Неизменность старых фото доказывает прежняя проверка
инвентаря до/после; команда не получает права изменять файлы. Запись эффекта,
ревизии и квитанции — одна транзакция. Ответ содержит доказательство rename и
метаданные свежести, без полного списка/вещи. Старый list.update сохранён.

## Проверено

- 89 целевых серверных проверок команды, журнала и сохранения старых фото.
- 63 клиентских проверки транспортной очереди, включая выключенный флаг,
  отсутствие capability, небольшой запрос, потерю ответа, повторное чтение
  квитанции и отказ от подменённого результата.
- 6 узлов изолированного HTTP/MySQL-прогона без пропусков. Новый сценарий
  использует настоящий клиентский адаптер и API: ответ после COMMIT теряется,
  новая очередь читает исходную квитанцию, POST один. Две разные вещи от одной
  базы принимаются; та же изменённая вещь и отсутствующая вещь отклоняются;
  прежний полный формат работает. В ядре изменений нет.

Логи frontend node_modules/.cache/compact-rename-{client-tests,mysql}.txt,
API node_modules/compact-rename-tests.txt. GitHub Actions не использовался.
Это проверка договора/транспорта, не проверка обычной формы в браузере.

## Следующий ограниченный шаг

1. Подключить компактный capture к обычному переименованию, с общей границей
   порядка для новых и старых команд. В очередь писать команду и ссылку на общую
   подтверждённую базу, а не отдельные полные снимки на каждое переименование.
2. Сохранить чтение старых записей и согласовать компактные команды с последующим
   полным/составным действием. Не вводить вторую независимую пишущую очередь.
3. Применять подтверждение к базе, сохраняя более поздние местные команды;
   неподтверждённый ответ сам по себе не даёт повторного POST или нового UUID.
4. Проверить офлайн/перезапуск/другое устройство и два быстрых переименования
   в собранном UI. Старый нерегулярный сбой v1625 отложен пользователем;
   причина неизвестна, переполнение не подтверждено.
5. Затем серверный выпуск с поддержкой обоих форматов, клиентский выпуск и
   отдельная проверка на телефоне. Частичная загрузка и офлайн-каталог не входят.

Обычные правки переводятся постепенно. Копирование дерева, импорт, восстановление
и файловые изменения остаются согласованными составными операциями; их не следует
дробить на независимые записи, способные оставить половину результата.
