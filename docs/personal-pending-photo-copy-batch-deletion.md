Исходная массовая копия проверена в FE `ce9bdfa` / API `6a81211`.
Продолжение сервера зафиксировано локально в `d39d61c`.
Новый `PERSONAL_PENDING_PHOTO_COPY_BATCH_DELETION_ENABLED = false`;

Возможность `personalCausalPhotoCopyBatchDeletionV1` требует прежних gates
массового копирования и удаления после копии.

## Сохранённый состав

Тот же механизм зависимостей одиночной копии принимает массовый результат.
`photoResults.version: 2` содержит operationId исходного batch и полный список
владельцев в исходном порядке, включая владельцев без фотографий. Список нельзя
сократить до оставшихся на экране копий. Сама копия и её body/hash не меняются.
Каждое последующее удаление зависит от непосредственного предшественника и
исходного batch; одинаковая прямая зависимость у первого удаления не дублируется.

Разрешены явные удаления источников и копий по одному или последовательно.
Каждая оставшаяся копия сохраняет все выбранные поля и pending-фото. Удалённая
копия или источник не могут появиться снова, в том числе как запись с пустым
photos. Вычисляемые пустые поля размещения не превращаются в новое размещение.
Посторонние фото должны быть подтверждены и сохранены без изменений.

Сервер после зависимостей и CAS сверяет полную исходную квитанцию batch:
аккаунт/список/тип, всех владельцев, все результаты фото, ID, assets и порядок.
Только затем private execution view получает подтверждённые фото выживших
копий. Для уже удалённой на предыдущем шаге копии нужна точная квитанция этого
шага. Пропуск владельца без фото — такая же ошибка, как пропуск фотографии.
Нельзя подменить pending-ссылки предполагаемыми URL или заново прочитать источник.

Обычная транзакционная проверка удаляет владельцев и записывает tombstones
фото вместе с бизнес-сохранением и квитанцией. Физические файлы не перемещаются
и не удаляются этим адаптером. Старый SAVE/receipt не воскрешает удалённые строки.

## Восстановление и отмена

Неизменённый бизнес-снимок при выборе сохранённой укладки разрешает читателю
дойти до окна восстановления даже с выключенными writers. Новое действие
для такого выбора не регистрируется. Потерянная квитанция требует чтения по
прежнему ID. Подтверждение предшественника не становится текущим экраном.

Отмена исходного batch делает зависимые удаления неизменно отклонёнными.
Клиент проверяет исходный пакет и отклонённого непосредственного предшественника
перед терминализацией следующего удаления. Независимые неизвестные операции
не получают разрешения на повтор. «Решить позже» сохраняет журнал; отдельное
«Оставить серверную версию» создаёт собственное новое действие.

## Проверки и продолжение

**137/137 API/MySQL**, 81,81 с, без пропусков (`pending-copy-batch-mysql-2.log`):
часть источников/копий, несколько удалений, копия без фото, обратная доставка,
потеря ACK и restart, неполные ссылки на результат, tombstones и replay,
отмена с потерей ответа и отдельный keep-server. **453 transport**, **56
operation**, **74 source/service**, **895 critical**, source checks прошли.
**28/28 UI Chromium/mobile WebKit**, 9,9 минуты, без повторов во втором прогоне
(`pending-copy-batch-ui-2.log`). Первый прогон остановился после 12 успешных
сценариев на сравнении полного журнала в нестабильном порядке localStorage.
Тест теперь сравнивает все записи по ID; содержимое и причинный порядок не менялись.

Первый прогон обнаружил обращение к свойству у boolean false в отмене прежней
одиночной формы; исправлено без изменения её поведения. После подтверждения
очередь может законно убрать старую локальную запись при checkpoint, поэтому
тест проверяет неизменность фактически отправленного body и квитанции. Новая
unit-проверка также закрыла возвращение удалённого источника с photos:[] уже
на первом шаге удаления.

Следующие открытые задачи: деревья и укладки с фото, изменение ещё не
подтверждённого источника перед копированием, архивы/обмен/admin и остальные
пункты общего списка. Все новые флаги выключены; push/deployment не выполнялись.
