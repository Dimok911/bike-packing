# Личный архив с фотографиями

Локальная реализация принята для описанного ниже среза. Не включать release gates и не
публиковать эту ветку. Раздел 09 целиком ещё не закрыт.

`list.import` с `archiveImport.version = 2` хранит исходный архив, выбранный
режим, точные целевые укладки и полный упорядоченный перечень фотографий.
`PERSONAL_ARCHIVE_PHOTO_IMPORT_ENABLED = false`; capability
`personalCausalArchivePhotoImportV1`. API дополнительно требует выключенный
по умолчанию `BIKE_PACKING_CAUSAL_ARCHIVE_PHOTO_IMPORT_ENABLED`.

До первого ожидания фиксируются источник, выбор укладок, метаданные, новые
номера фотографий и assets. Байты выбранных файлов снимком отделяются от
изменяемого Map архива. Затем проверяются SHA-256 оригиналов и вычисляются
хеши превью. Один исходный файл для нескольких вещей или сумок получает
отдельные привязки на каждую цель. Порядок внутри владельца сохраняется.

Полный импорт заменяет прежние ссылки новыми и включает неразмещённых
владельцев. Частичный импорт сохраняет текущие поля существующих вещей/сумок
и их подтверждённые фотографии; недостающие выбранные ссылки добавляются
в порядке архива. Ссылка с прежним ID в частичном архиве не заменяет текущую.
Неизвестный или неподтверждённый файл не считается готовой фотографией.

После подтверждения пользователем native IndexedDB сохраняет все части
и неизменяемое действие одной транзакцией. Только после привязки этой записи
к outbox меняется интерфейс. Двойное нажатие использует тот же promise и ID.
Сбой между файловым сохранением и outbox оставляет отдельную запись для
восстановления; новый импорт при такой записи запрещён. Аварийная выгрузка
включает исходные байты и полный открытый архив, даже когда редактор заблокирован.

Отправка сначала проверяет итоговую квитанцию импорта. Для каждого файла
используется существующая однократная native claim, затем точная квитанция
стадии. После потери ответа и перезагрузки известный номер проверяется чтением;
новый POST файлов под новым ID не создаётся. Владеющее действие отправляется
после всех обязательных частей.

В SQL транзакции API повторно составляет план из подтверждённого текущего
списка, проверяет исходный manifest, привязки и фактические хеши staged files.
Новые фотографии, восстановленные владельцы, удаления прежних ссылок,
укладки, история, версия и итоговая квитанция фиксируются вместе. Файловых
записей и загрузок URL внутри этой транзакции нет. Существующие запреты
обычной формы на оживление удалённого ID сохраняются; восстановление владельца
разрешает только серверный адаптер архива под точной версией списка.

Отмена сначала фиксирует запрет выполнения всего импорта, затем подтверждает
каждую файловую часть. Готовые файлы остаются доступны для восстановления,
неотправленные части получают точные квитанции отмены. Выбор актуальной
серверной версии сохраняется отдельным действием, без наследования manifest
импорта. Байты не удаляются автоматически.

Ограничения текущего среза: личный режим, известный подтверждённый список,
до 50 частей и 50 МиБ, до 10 МиБ на файл. Не включает гостевой перенос,
административный архив, публичный импорт и редактирование зависимого
неподтверждённого архива; эти части остаются в общем списке.

Проверено: 514 transport, 895 critical, 60 operation, 74 source/service,
frontend check; 182/182 real API/MySQL за 194,34с на bundled Node24.19
(archive-photo-mysql-4.log); 18/18 Chromium/mobile WebKit за 4,8 минуты
(archive-photo-ui-4.log). Все тестовые процессы и сервисы завершены. Логи в
ignored node_modules/.cache/causal-evidence/2026-09-08/.

Браузерные сценарии проверяют реальные кнопки/ZIP/native IndexedDB:
full/replace/copy, lost last-file/owner ACK, reload, точный порядок,
следующую DB правку после подтверждения, native/queue quota и выгрузку всех
исходных байтов, отмену частичной загрузки с потерянным ответом, отклонённый
импорт и потерю ответа на явный выбор серверной версии. API дополнительно
проверяет unplaced/revived owners, fileless import, altered/missing stages,
две поздние SQL ошибки и отсутствие частичных бизнес-записей.

Первые UI прогоны выявили зависимость аварийного чтения от editing latch и
остановку отмены при неизвестном результате собственного stage. Контекст
чтения теперь доступен после ошибки, запись отдельно требует открытый editor.
Cancellation-only import может пройти только свой точный stage с совпадающими
owner/action/photo/asset/file/thumbnail hash. Обычная отправка и посторонние
записи остаются запрещены; такой transport record не может dispatch исходный
импорт. Отрицательные подмены и real lost-stage cancellation проверены.
