# Фотоформы до подтверждения гостевого переноса и архива

Локальное продолжение разделов 06 и 09 принято 2026-09-10. Рабочие флаги
выключены. Публикация сайта, push и изменения рабочих баз не выполнялись.

## Поведение

После подготовки гостевого переноса или личного архива можно добавлять фото
к уже существующей в подготовленном снимке вещи или сумке, удалять и менять
порядок выбранных фото вместе с полями карточки. Следующая форма может
относиться к другому владельцу. Обычные правки и явное удаление владельцев
между фотоформами сохраняют связи со всеми необходимыми предшественниками.

Исходный перенос, новые формы и последующие правки получают отдельные
неизменяемые действия. Перезапуск восстанавливает те же ID, данные и файлы.
Потерянный ответ проверяется по прежнему действию. Отмена сначала получает
точные подтверждения для исходных действий и файлов; исходные файлы остаются
доступны для восстановления и экспорта. Выбор актуальной серверной версии
сохраняется отдельным решением.

Поддерживаются guestImport v1 и archiveImport v2, включая отсутствие файлов
у исходного импорта. При включении нового режима интерфейс использует v2 и
для новых личных архивов без фото, чтобы последующие файлы имели тот же
протокол зависимости. Уже сохранённые DB-only архивы v1 не переписываются.
Обработка административных архивов остаётся отдельным пунктом раздела 11.

## Неизменяемый протокол

- `ownerResult.version=3` содержит непосредственного родителя, исходный
  `importOperationId`, тип `importKind` (`guest` или `archive`), полный снимок
  владельца и упорядоченный состав всех ожидающих фото разных владельцев.
- `photoResults.version=9` связывает дальнейшую DB-правку с последней
  фотоформой. В зависимостях сохранены непосредственный родитель, фотоформа
  и корень импорта. Обычные предшественники исходного архива/гостевого переноса
  сохраняют прежние версии ссылок 3/4.
- Серверная квитанция содержит `importPhotoForm` с типом и корнем импорта,
  полным ожидающим составом и `importPhotoFormSourceOperationId`. Эти поля
  появляются только после успешной проверки исходной операции и её результата.
- Сервер проверяет корневую квитанцию, исходный файловый манифест, хеши,
  владельцев, подтверждённые замены файлов, обе зависимости и версию списка.
  Фактическую версию владельца читает под блокировкой строки. Условные номера
  версий в журнал, запрос или базу не записываются.
- Гостевой перенос, архив и публичная копия не взаимозаменяемы. Совпадения ID
  недостаточно. Отсутствующая квитанция с происхождением не заменяется свежим
  чтением источника. Удалённая вещь не появляется снова из старого снимка.

Чистая проверка состава использует ранее проверенную общую грамматику фото
публичных копий через временное представление. Оно существует только внутри
валидатора; сохранённые запросы и квитанции имеют отдельный тип guest/archive.

## Выключатели

Клиент: `PERSONAL_IMPORT_PHOTO_FORM_ENABLED=false`.

Сервер: `BIKE_PACKING_CAUSAL_IMPORT_PHOTO_FORMS_ENABLED=1` вместе с разрешениями
фотоформ, зависимых форм и соответствующего гостевого либо архивного импорта
и его потомков. Возможность сервера: `personalCausalImportPhotoFormsV1`.
Наличие архивного разрешения не разрешает гостевой корень и наоборот. Клиент
проверяет поддержку выбранного вида импорта и его зависимых правок отдельно:
общая возможность сервера может быть включена только для другого вида.

Без нового разрешения клиент останавливается до записи очереди/файлов либо
сетевой отправки продолжения. Старый сервер не позволяет начать отправку
нового файла, формы, DB-потомка или отмены через неподдерживаемый протокол.
Чтение сохранённой цепочки и экспорт доступны при выключенных писателях.

Проверены 20 новых модульных сценариев клиента, 795 transport, 896 critical,
108 серверных operation-тестов и 74 source/service. Первый законченный парный
проход: 18/18 API/MySQL. Итог нового полного серверного прогона:
**360/360 API/MySQL**, 770,02 с, exit 0, включая 21 новый сценарий этого
продолжения и выбранные архивные укладки. Временная MySQL остановлена штатно.

36 разных сценариев интерфейса прошли в Chromium/mobile WebKit: исходный
импорт с файлами и без файлов, формы разных владельцев, явное удаление,
нехватка места, замена/порядок фото, отмена, потерянный ответ отмены, выбранные
укладки в режимах замены и копирования. Это совокупность проверок ui-5,
ui-6 и ui-7, а не один безошибочный запуск: первые два прохода останавливались
на ожидании более пяти секунд. В трассах отмена/продолжение ещё выполнялись;
для сетевого завершения задано 30 секунд без повторного нажатия. Последний
контрольный проход ui-7: 12/12, включая обе отмены на обоих браузерах.
Отдельный выключенный режим ui-off-1: 8/8; открытые формы, поля и файлы
сохраняются без старого обходного запроса. FE source check, обычная и
изолированная браузерная сборки прошли. Новые проверки transport и server
source выполнены также после уточнения поддержки выбранного вида импорта.
Скриншоты компьютерного гостевого и мобильного архивного сценария просмотрены.

Первый полный API/MySQL прогон остановлен общим лимитом в десять минут;
последующие дочерние проверки были отменены родительским тестом. Для выросшего
набора оставлен конечный лимит 30 минут. Результат оборванного запуска не
считается приёмкой. Обработчики и серверные дедлайны этим не менялись.
