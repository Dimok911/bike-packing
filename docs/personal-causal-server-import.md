# Серверный импорт: следующий адаптер раздела 10

Инвентаризация 10.09.2026. Пункт пока открыт; публикация и Shared Auth не входят
в эту работу. Это продолжение после отдельного адаптера создания ссылок.

## Найденные пути

- `handleBikePackingListImport` читает источник и цель до транзакции,
  назначает ID при каждом запросе и копирует файлы до блокировки цели.
  Перенаправление старого POST в очередь не делает такой порядок атомарным.
- `runCausalPublicLayoutCopy` и связанные личные копировщики явно останавливают
  `layout.linkedSharedList`. Обычное копирование публичного шаблона не является
  разрешением читать чужой private список, стоящий за живой ссылкой.
- Живая ссылка хранит отдельный неизменяемый выбор области, но её содержимое
  определяется текущей версией источника. Revision строки ссылки недостаточна
  для фиксации выбранной пользователем версии содержимого.
- Снимок имеет собственные проверенные файлы; для живой ссылки файлы читаются
  из выбранной области исходного списка. Публичный GET не должен создавать
  файловые копии даже ради будущего импорта.

## Требуемая реализация

1. Отдельное сохранённое намерение serverImport с собственным выключенным
   флагом и capability. Источник, область, точный снимок, версия цели, новые ID
   владельцев/укладок/фото и все обязательные файлы фиксируются до ожиданий.
2. Версия чтения ссылки должна подтверждать её неизменяемый выбор и конкретную
   версию содержимого. Повтор не перечитывает новую живую версию вместо выбранной.
3. Сервер разрешает источник только по действующему праву чтения ссылки;
   это не расширяет личный runner до произвольной записи в чужой список.
   Все фактические агрегаты источника и назначения блокируются в едином
   порядке, включая private источник живой ссылки, затем проверяются версии.
4. Общая детерминированная грамматика личных копий может использоваться внутри
   адаптера, но журнал, запрос, проверка источника и квитанция остаются
   явно serverImport. Публичный шаблон не подставляется вместо пользовательской ссылки.
5. Новые строки, файлы, ID-карты, данные цели и квитанция входят в один итог
   операции. Нет частично успешной копии при недоступном обязательном файле.
   После потери ответа повторяется тот же UUID и тот же файловый план.
6. Реальные кнопки копирования всей укладки, вещи, сумки/поддерева и оболочки;
   выбор цели, количества и позиции; дальнейшие действия и восстановление.

Приёмка: source A изменён → выбранная копия B → A удалён, обратная доставка,
повтор, потеря ответа/reload, недоступный/изменённый файл, смена владельца или
контекста, quota и OFF. Сначала точный API/MySQL-набор, затем реальные кнопки
Chromium/mobile WebKit и чтение созданной личной копии. До этих проверок
третий критерий раздела 10 не отмечается выполненным.
