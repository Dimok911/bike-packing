# Личная история с подтверждёнными фотографиями

Новый выключенный gate допускает `historyRestore.version: 2` с полным
`photoRestore` manifest. Старый version 1 по-прежнему относится к DB-only
истории. Preview запрашивается с `photos=1`; нужны отдельный frontend gate
и server capability. Production и развёрнутый Experiment не менялись.

История и текущая цель фиксируются history ID/hash, выбранными layout IDs,
числовой revision списка и хэшем полного результата. Фото-план включает весь
реестр прежних публикаций (в том числе удалённых), исходных владельцев, asset
IDs, полные подтверждённые ссылки, версии и точный порядок выбранных фото.
UUID обозначают идентичность; порядок определяется версиями и зависимостями.

Сервер повторно собирает план под блокировкой списка, сверяет владельца,
историю, фото-строки, неизменяемые staged receipts, пути и метаданные. Для
каждого требуемого фото проверяются SHA-256 сохранённого файла и миниатюры.
Он не создаёт новые asset IDs и не угадывает ссылку по похожему имени.

Ссылки возвращаются/удаляются в одной SQL-транзакции с владельцами, историей,
числовыми версиями и итоговым receipt. Общая проверка photo publication
остаётся обязательной. Байты не перемещаются и не удаляются восстановлением.
Ошибка поздней записи откатывает также возвращённые и удалённые ссылки.

Frontend сохраняет действие до изменения экрана, проверяет фото-состав
локального снимка, сохранённой очереди и server receipt. После reload и
потери ответа используются прежние ID/байты. Следующее изменение не наследует
manifest восстановления. Отклонённое восстановление требует отдельного выбора
«оставить серверную»: обе версии и прежние receipts сохраняются до подтверждения
этого нового действия. Автоматического переноса restore на новую базу нет.

Восстановление одной укладки сохраняет действующие общие каталожные записи,
включая их нынешние фото; отсутствующий владелец возвращается из выбранной
истории. Это прежняя семантика scoped history. Полное восстановление возвращает
выбранные исторические ссылки и порядок, а лишние текущие ссылки помечает
удалёнными. Административная история относится к отдельному открытому разделу.

Локальная проверка: 166/166 API/MySQL на bundled Node 24.19.0
(`photo-history-mysql-3.log`, 197,97 с), 491 transport, 895 critical,
60 operations, 74 source/service, FE source check. Включены точные возвраты
удалённых вещей/сумок, откат SQL, испорченный файл, изменённый manifest,
неверный владелец, full/scoped restore, reverse delivery, lost ACK/restart,
отклонение с зависимым действием и явным keep-server, compaction/replay.
22/22 UI прошли после финального исправления базы (`photo-history-ui-3.log`,
5,8 минуты, Chromium и mobile WebKit, без повторов). API `47bf753`.
Все процессы завершены. Предыдущий UI прогон также прошёл 22/22.
Отдельный regression воспроизвёл ошибочный выбор прежней базы при наличии
нового подтверждённого изменения; теперь выбирается база актуальной вершины.
