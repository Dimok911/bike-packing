# Гостевой перенос через причинную очередь

Состояние на 2026-09-09: подготовка полного источника, устойчивый журнал,
серверная транзакция, реальный вход, общая очередь, восстановление и отмена
подключены и проверены локально. Раздел 09 целиком не закрыт: продолжения
незавершённого гостевого переноса и составные формы ещё предстоят. Все
release gates выключены; публикаций и push нет.

## Зафиксированное действие

Новый list.import с guestImport.version=1 и capability
personalCausalGuestImportV1. Серверный флаг
BIKE_PACKING_CAUSAL_GUEST_IMPORT_ENABLED требует личную причинную очередь,
стейджинг файлов и публикацию фото. Архивные флаги не включают гостевой импорт.

Снимок содержит полный гостевой источник, выбранные укладки, фиксированные
имена, отображение source ID → target ID, reuse существующих личных записей,
новые UUID фотографий/активов, метаданные правки, исходную личную revision и
SHA-256 источника/результата. UUID фиксируются до чтения файлов и ожидания.
Содержимое Shared Auth не менялось; email/данные входа остаются в локальном
журнале и не включаются в серверный manifest.

Копирование сохраняет бизнес-поля, заметки, размеры и происхождение шаблона,
удаляя активные публичные привязки и зеркала размещений. Размещения, порядок,
количества, отметки упаковки и отдельные вещи переносит чистый компилятор.
Одна запись, используемая несколькими укладками, сохраняет один target ID.
Разные гостевые IDs одинаковой записи из шаблона могут использовать уже
созданную копию в следующей укладке. Повторное использование личной записи
сохраняет все её поля и существующие фотографии по прежним правилам reuse.

Известный старый формат без arrangement проецируется на отдельной копии.
Циклы, неоднозначные связи и повреждённый существующий arrangement вызывают
остановку; исходный снимок не ремонтируется. Сохраняются и исходные количества,
и отметки упаковки старого формата.

## Журнал и файлы

Отдельная IndexedDB хранит полный выбор одной strict транзакцией с уникальным
ключом полного handoff + actor/environment/list. Две вкладки получают один
неизменяемый выбор. Смена базы не переписывает его operation ID или payload.
Чтение доступно при выключенном writer; повреждение, quota и смена аккаунта
останавливают продолжение. Очистка/TTL неподтверждённых записей отсутствуют.

Первый браузерный прогон обнаружил, что сортировка ключей при сериализации
ломала существующий JSON fingerprint гостевого handoff. Журнал теперь хранит
исходный порядок ключей; канонический JSON используется отдельно для SHA-256.
Второй прогон прошёл полностью.

Файловый кодек сохраняет настоящее действие list.import, полный снимок,
состав фото и исходные байты. Проверяются принадлежность каждой записи,
MIME/размер, SHA-256 и порядок ссылок. Полученные до ошибки файлы доступны
для явного восстановления. Лимиты: 50 файлов, 50 MiB суммарно вместе с
миниатюрами, 10 MiB на часть.

## Сервер

Один защищённый контекст передаёт actor ID, operation ID и соединение БД.
Гостевой обработчик доступен только через list-operations; обычного прямого
HTTP writer нет. Под блокировкой revision компилятор заново проверяет
результат относительно текущей личной базы. Все новые IDs проверяются по
строкам владельцев и укладок, включая tombstones и записи без фото.

Проверка staged файлов на диске, ссылки, сущности, укладки, история, CAS и
квитанция выполняются в общей транзакции. Гостевой импорт не воскрешает старый
ID. Общий исполнитель фото переиспользуется архивом с его прежним явным
разрешением восстановить архивные записи. Ошибки SQL доходят до rollback,
сохраняя возможность повторить исходный UUID.

Копии 11 чистых исходных модулей находятся в API src/lib/guest-import.
source-hashes.json и модульная проверка контролируют их код с нормализацией
только CRLF → LF. При изменении общего компилятора обновлять обе стороны и
manifest; исходные правила публичного копирования здесь используются только
для преобразования частной копии.

## Подключённый вход и восстановление

Реальный вход в личный Experiment фиксирует выбор до чтения файлов, затем
сохраняет исходные байты в native IndexedDB и связывает действие с общей
очередью до изменения экрана. Декодеры читают гостевые записи и при откате
writers; отправка требует собственного guest gate и capability. Обычное
сохранение не может скрыто провести guestImport через архивный обработчик.

Загрузчик читает именно гостевое пространство кеша после входа. Принимается
проверенный оригинал; удалённый кеш дополнительно связан с точной исходной
ссылкой. В противном случае загружается оригинал, а не подменяющая его
миниатюра. Все ID и исходное содержимое остаются прежними при повторе.

Если редактор добавил только известный отсутствующий marker миграции
количеств arrangement.itemQuantityMigrationVersion=3, он сохраняется отдельным
причинным DB действием до выбора импорта. Любое другое расхождение с базой
останавливает подготовку; строгий компилятор не ослаблен.

Журнал выбора сохраняет compact intent {version,files,causal} перед native
capture. Из него и полного immutable selection восстанавливается точный body
после compaction очереди. Completion записывается только по точной committed
квитанции после подтверждённой текущей базы; hash, actor, list, kind, ID и
revision проверяются повторно. Чтение completion работает при выключенных
writers и исключает второй импорт того же handoff.

Разрыв native files → outbox link восстанавливается явно: сохранённое действие,
снимок, исходная база и байты связываются с прежним operation ID. Повторное
чтение исходного URL не требуется. Восстановление не меняет экран и не
отправляет запрос само; далее обычная очередь проверяет серверную revision.
Несовпадение intent, аккаунта или чужая незавершённая запись блокирует связь.
Recovery ZIP включает полный выбор (в том числе сырую повреждённую запись),
несохранённую форму и доступные оригиналы.

Гостевой raw workspace, handoff и кеш сохраняются после успеха. Несколько
удалений localStorage не атомарны с другой гостевой вкладкой, поэтому такой
автоматической очистки нет. Долговечный completion предотвращает повтор.
Более новая гостевая работа, появившаяся во время переноса, остаётся целиком.
Rejected/отменённый перенос требует явного решения; keep-server убирает
guestImport из нового решения, сохраняя исходник и прежние квитанции.

## Подтверждённые проверки

- API/MySQL: 198/198, guest-wiring-mysql-1.log, 218,65 с. Помимо прежних
  compiler/SQL rollback/restart/reverse arrival случаев, четыре сценария
  проводят настоящий frontend queue/staging/drain/cancel через API: с фото
  и без, частичный ACK файлов, потеря owner/cancel ACK, перезапуск, более
  новая серверная правка, точный прежний ID и отдельное keep-server решение.
- Chromium/mobile WebKit: 24/24, guest-import-ui-7.log, 2,2 мин. Настоящие
  IndexedDB и вход после возврата Shared Auth; complete source/native bytes,
  две вкладки, writer rollback, quota/corruption, потеря ACK, частичная
  загрузка, отмена, recovery ZIP после reload и восстановление разрыва связи
  без доступного исходного URL. Проверен более новый гостевой workspace.
- Регрессия архивов: 48/48 Chromium/mobile WebKit,
  guest-archive-regression-1.log, 11,4 мин; включая прежние pending descendants.
- Frontend transport: 557/557, guest-wiring-transport-2.log; critical: 895/895,
  guest-wiring-critical-1.log; FE check: guest-wiring-check-2.log.
- API operations: 67/67, guest-wiring-operations-1.log; service/source: 74/74,
  guest-wiring-source-1.log. Зеркала чистого компилятора не менялись.
- Ранние UI прогоны обнаружили слишком раннюю фиксацию handoff в fixture,
  отсутствующий migration marker и неверный thumbHash fixture. Handoff теперь
  фиксируется по реально сохранённому гостевому состоянию при возврате auth;
  marker проходит отдельное DB действие; thumbHash соответствует API.
  Проверки полного payload и источника сохранены. Прогон 6: 8/8, затем
  расширенный прогон 7: 24/24 без пропусков.

## Следующая работа

Дочерние правки/удаления во время гостевого переноса пока не подключены к
его собственным результатам. Составные формы и изменение фото во время
импорта, публичные/административные архивы и общий протокол безопасной
очистки остаются в списке. Гостевой manifest нельзя направлять в resolver
archiveImport.version=2 или считать такой обход поддержанным продолжением.
