# Копирование записей внутри административного шаблона

Продолжение раздела 11 от 10.09.2026. Источник и цель находятся в одном
подтверждённом demo/shared шаблоне. Подключены настоящие кнопки копирования
вещи и корневой сумки в каталог, а также выбор нескольких записей.
Копия сумки здесь пустая: дерево и содержимое источника остаются на месте.
Новые копии не размещаются в укладке, фотографии требуют следующего адаптера.
Публикаций приложения нет, рабочие флаги OFF.

## Сохранение выбора

До окна подтверждения фиксируются выбранные записи, снимок редактора, его
версия, новые ID и время правки. Подтверждение проверяет тот же аккаунт,
административный режим, редактор и снимок. Изменившийся источник не копируется
по новому содержимому незаметно для пользователя. Повтор нажатия не использует
одну подготовку дважды. Все выбранные копии сохраняются одним планом.

Для этого действия достаточно существующего `template.save`: одна исходная
revision защищает одновременно источник и цель. Его серверные проверки прав,
конфликта и атомарного эффекта/квитанции остаются прежними. Отдельный внешний
источник здесь не читается. Перенос между шаблонами требует другого адаптера
с самостоятельной проверкой источника; `template.copy` целого шаблона описан
отдельно в `admin-template-causal-copy.md`.

Новые записи теряют служебные ID и происхождение исходного demo/shared,
затем получают принадлежность текущему каталогу. Это необходимо, чтобы экспорт
не сопоставил независимую копию с исходной записью по `sharedSourceId` или
`publicCatalogItemId`/`publicCatalogContainerId`. Исходные записи и размещение
остаются прежними; сохраняются поля выбранной вещи/сумки и новые независимые ID.

Количество размещённой вещи принадлежит arrangement; её запись каталога
нормализована до единицы. Копирование в каталог берёт эту единицу, а у вещи
вне укладки сохраняет собственное количество. UI-проверка обнаружила перенос
количества из размещения в копию shared; причина исправлена без ослабления
проверки. Дополнительно первое открытие shared теперь использует существующую
проекцию подготовленного серверного снимка, как при принятии серверного варианта.
Старый путь публичного копирования сбрасывал количество detached-вещи до единицы
и пересобирал размещение. Новая проекция сохраняет каталог, связи, порядок,
количество и отметки упаковки, затем назначает отдельные местные ID.

## Хранение и восстановление

До POST записывается проверенное локальное зеркало с полным планом v1 в
`adminCausalCopyPlan`. Для копии целого шаблона этот же указатель по-прежнему
содержит план v3; восстановление строго проверяет оба формата и их binding.
План каталога может содержать только одно `template.save` от исходной revision,
с прежней видимостью и без отдельной команды публикации.

При отказе первого зеркала новые записи убираются, исходные данные остаются,
POST отсутствует. При отказе журнала подготовленный план и все новые ID уже
сохранены; reload завершает ту же подготовку. Ожидающий черновик отмечается
несохранённым до записи журнала, поэтому фоновое обновление не заменяет его
серверным снимком. После отказа записи ссылки редактора исходный план и этот
признак сохраняются. Порядок шаблонов и обычные команды не обходят подготовку.
Конфликт сервера удерживает ту же копию и UUID для последующей сверки.
