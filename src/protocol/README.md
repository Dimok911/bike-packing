# Ядро подтверждаемых операций — первая версия

## Ядро протокола / Protocol Core: текущая архитектурная граница

Проверенный срез 17.09.2026, матрица девяти инвариантов, границы SQL/staged
атомарности, пути вне этого модуля и узкое legacy-правило Tristan:
[docs/PROTOCOL-CORE.md](../../docs/PROTOCOL-CORE.md).

Этот каталог содержит переносимые identity/journal/delivery. Универсальные
зависимости, CAS/rebase, целостность каталога и файлов, серверные транзакции
не реализованы здесь: их обеспечивают отдельные адаптеры. Административный
whole-copy пока использует собственный защищённый клиент. Завершение первой
версии модуля не означает охват всего приложения. Ниже — его договор адаптеров.

Вход: `src/protocol/index.js`. Модуль не зависит от Bike Packing, DOM,
localStorage, IndexedDB, HTTP или Node. Bike Packing и пример
`examples/confirmed-notes` используют одинаковый код ядра.

## Граница ядра

- `matchesOperationIdentity`: сравнение номера, пространства приложения,
  владельца, ресурса, команды и digest неизменного содержимого.
- `canonicalOperationJson`: существующая канонизация JSON, без смены
  формата хеширования Bike Packing. Схему входных данных проверяет адаптер.
- `createOperationJournal`: поиск, запись намерения и подтверждения через
  синхронное либо асинхронное хранилище. Проверяет идентичность, повторно
  читает записанное содержимое и подтверждение. Номер с другими данными
  не является новой операцией.
- `createConfirmedDelivery`: запись до отправки, одна отправка, чтение
  исходной квитанции при неизвестном результате, восстановление после
  перезапуска и ограниченное возобновление по разрешению адаптера.

Версия внутреннего договора идентичности — 1. Это не новая версия HTTP
API и не миграция существующей очереди. Проекция идентичности:

```js
{ id, namespace, owner, resource, kind, digest }
```

Все поля — непустые строки. Формат ID, права владельца, алгоритм digest,
лимиты и допустимые команды уточняются адаптером. В Bike Packing сохранены
UUID v4 и SHA-256 от прежнего canonical JSON; номер операции не включён
в digest. На сервере владелец берётся из аутентифицированной сессии.

## Договор хранилища

`createOperationJournal` принимает:

- `read(id)`: прочитать запись в текущей области аккаунта/приложения;
- `writeIntent(intent)`: долговечно записать новый ID; при уже занятом
  номере атомарно отказать, в том числе при гонке нескольких вкладок;
- `writeConfirmation(entry, proof)`: сохранить квитанцию, вернуть `true`;
- `identityOf(entry)`: проекция идентичности;
- `contentOf(entry)` и `captureContentOf(intent)`: неизменное содержимое
  из сохранённой записи и входного аргумента соответственно;
- `confirmationOf(entry)`: прочитать сохранённое доказательство;
- `error(code, id)`: необязательное отображение ошибок в ошибки приложения.

Вызывающий код держит блокировку своей очереди от выбора записи до
завершения отправки. Проверка «записи ещё нет» сама по себе не заменяет
блокировку или уникальный ключ хранилища. Bike Packing сохраняет нынешние
Web Locks и ключи журнала; новое хранилище или перепись старых записей
для подключения ядра не требуются.

## Доставка и восстановление

1. `deliverNew` разрешён только для нового намерения. Ошибка записи или
   контрольного чтения не разрешает сетевую отправку.
2. `assertReady` / `assertCurrent` — синхронные проверки текущего аккаунта
   и поколения редактора. Последняя проверка выполняется без `await`
   перед началом отправки.
3. `accept(entry, response)` адаптера проверяет терминальный результат и
   сохраняет его доказательство через journal.confirm. Один HTTP 200
   не является подтверждением операции.
4. После ошибки отправки ядро читает квитанцию исходного номера. Обычный
   `recover` также только читает. Unknown, timeout, 404 и потерянный ответ
   не разрешают POST, новый UUID или обход очереди.
5. `prepareRecovery` может вернуть `{ receipt, beforeDispatch }` только
   после проверки свежего серверного разрешения на повтор **того же**
   намерения. В Bike Packing это existing waiting/prepared protocol;
   проверки capabilities, зависимостей и восстановления остались в адаптере.
6. Квитанция — историческое подтверждение. Перед изменением экрана
   приложение отдельно проверяет текущий аккаунт, поколение и свежесть
   серверной версии. Rejected не означает, что правка применена.

Офлайн-намерение сохраняется в прежнем долговечном журнале. После
возвращения сети продолжается тот же ID; неподтверждённые данные нельзя
автоматически удалить или заменить. При истечении срока хранения
квитанций нужен отдельный договор сервера, а не бесконтрольная повторная
отправка. В первой версии новый механизм очистки/истечения не добавлен.

## Серверный адаптер Bike Packing

Остаются прежними HTTP-маршруты, `list.update`, полный payload, проверка
владения и транзакционный исполнитель. Уникальность серверного журнала:
`(environment, actor_id, operation_id)`. Повтор с иным digest/kind/listId
отклоняется; повтор терминального намерения возвращает сохранённую квитанцию.

`bike-packing-list-operations.js` фиксирует бизнес-изменение, ревизию и
квитанцию одним COMMIT. Отклонение откатывает эффекты до SAVEPOINT, сохраняя
отказ. Вложенный commit прежнего обработчика контролируется адаптером
`bike-packing-list-operation-context.js`. Это проверяется на настоящей
MySQL, а не заменяется имитацией транзакции внутри клиентского ядра.

Таким образом, серверная БД/авторизация остаются адаптерами. Отдельный
универсальный SQL-исполнитель в этот модуль не входит. Пример заметок
использует свой серверный адаптер и ту же канонизацию, журнал и доставку.

## Ограничения первой готовности

Первый сквозной сценарий — переименование существующей вещи без изменения
файлов фото. Общий участок очереди используется и другими уже включёнными
операциями, но предметные обработчики, фото, миграции, rebase, UI и правила
доступа не перенесены в ядро. Публичного npm-пакета пока нет; модуль можно
подключать внутри репозитория и переносить вместе с адаптером второго проекта.
Частичная загрузка и новые офлайн-настройки остаются отдельными задачами.
